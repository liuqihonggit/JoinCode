# EXE / MCP 函数纵深防御验收规范

> 适用场景：EXE 通过启动参数触发命令，包含 300+ MCP 函数、数十条斜杠命令。
> 核心问题：返回码/控制台输出只代表「命令被调用」，不代表「业务模块真实生效」。
> 设计哲学：**纵深防御**——每一层自动拦截能拦截的问题，拦不住才下沉到下一层；用户介入是最后一道防线，不是默认选项。

---

## 一、体系总览：六层纵深防御

```
┌─────────────────────────────────────────────────────────────┐
│  第0层  预防层  统一参数格式 + 统一返回结构（写代码时就消除歧义）  │
├─────────────────────────────────────────────────────────────┤
│  第1层  快速扫描  脚本批量全量遍历，秒级定位崩溃/格式坏点（全自动） │
├─────────────────────────────────────────────────────────────┤
│  第2层  穿透探测  单命令六步深挖，区分「调用成功」vs「业务生效」    │
│                  （全自动，含反向查询、持久化校验、双重验证）       │
├─────────────────────────────────────────────────────────────┤
│  第3层  权限绕行  遇到 EACCES/Permission denied 自动逐级绕行      │
│                  （参数绕过→降级目录→sudo -n，全自动）            │
├─────────────────────────────────────────────────────────────┤
│  第4层  分片复测  拆成小份交接文档，多 AI 窗口并行人工体感复测      │
│                  （半自动，抓「词不达意」「交互不适」等隐性问题）   │
├─────────────────────────────────────────────────────────────┤
│  第5层  用户介入  手工验证桥接（最后防线，前四层都搞不定才触发）    │
└─────────────────────────────────────────────────────────────┘
```

**升级规则**：每一层有明确的「通过标准」和「失败升级条件」。当前层能自动修复的，就地修复，不往下传；当前层无法自动判定或自动修复的，才升级到下一层。

---

## 二、第0层：预防层（代码阶段，消除歧义）

> 目标：在写代码时就把问题消灭，不让它流到测试阶段。

### 2.1 统一启动参数格式（强制）

- 所有命令使用**同一套参数解析规则**，禁止特例。
- 发生过一次歧义（例如 `--key value` 和 `--key=value` 行为不一致），必须修复为两种都支持。
- 参数缺失时，返回**明确的用法提示**，不能静默失败或崩溃。
- 非法参数时，返回**标准化错误**，不能直接抛异常退出。

### 2.2 统一返回值结构（强制）

所有命令的 stdout 必须是统一 JSON 结构：

```json
{
  "error": false,
  "command": "memory_write",
  "message": "记忆写入成功",
  "data": { "key": "xxx", "value": "yyy" },
  "meta": { "duration_ms": 120, "persisted": true }
}
```

- `error`：布尔值，true 表示业务失败。
- `message`：**不允许为空字符串**，即使操作成功也要有描述。
- `data`：业务结果，空操作也要返回 `{}` 并在 message 说明。
- `meta.duration_ms`：执行耗时，**超过 30000ms 必须在 message 中提示用户**。
- `meta.persisted`：是否已持久化，涉及存储的命令必须标注。

### 2.3 禁止项

- ❌ 禁止空输出（`Error:false` 但 stdout 为空）。
- ❌ 禁止非结构化的零散文本输出。
- ❌ 禁止「设计限制」作为不实现的理由——交付阶段用不了 = 客户用不了。

---

## 三、第1层：快速扫描（脚本批量，全自动）

> 目标：全量遍历 300+ MCP 函数和斜杠命令，秒级定位明显坏点。
> 这一层**只做表层探测**，不校验业务逻辑正确性。

### 3.1 执行方式

- 脚本遍历所有命令，用启动参数调用 EXE。
- 每个命令传入**最小合法参数**（能触发即可）。
- 捕获：退出码、stdout、stderr、执行耗时。

### 3.2 拦截的故障类型

| 故障编号 | 现象 | 本层能否拦截 |
|---|---|---|
| 1 | 直接崩溃、边缘参数崩溃 | ✅ 退出码非0 / 进程异常 |
| 2 | 输入输出格式错误 | ✅ stdout 不是合法 JSON / 字段缺失 |
| 3 | 格式对了但 `error:true` | ✅ 直接读取 error 字段 |
| 4 | `error:false` 但空输出 | ✅ message 为空 / data 缺失 |
| 5 | 超时、死锁 | ✅ 耗时 > 阈值（默认 30s） |
| 6 | 词不达意（业务没执行） | ❌ 本层无法识别，升级到第2层 |
| 7 | 跨进程/沙箱不可用 | ❌ 本层无法识别，升级到第2层 |
| 8 | 真正成功 | ✅ 通过，标记为「表层通过」 |

### 3.3 通过标准

- 退出码 = 0
- stdout 是合法 JSON，包含 `error`/`message`/`data`/`meta` 四个字段
- `error` = false
- `message` 非空
- 耗时 ≤ 30s（超过则标记「需备注耗时」，但不直接失败）

### 3.4 失败处理

- 故障 1/2/3/4/5：**自动记录坏点清单**，输出命令名、现象、退出码、耗时。
- 能自动修复的（如格式不统一），直接修改代码后重跑。
- 本层结束后，所有「表层通过」的命令进入第2层；坏点修复后重跑第1层。

---

## 四、第2层：穿透探测（单命令六步深挖，全自动）

> 目标：对第1层「表层通过」的命令做深度验证，区分「命令调用成功」和「业务功能真实生效」。
> 这是整个体系的**核心层**，专门抓「词不达意」「静默失败」「持久化未实现」。

### 4.1 触发条件

- 第1层表层通过的命令，按**随机抽样 + 重点模块全覆盖**进入本层。
- 重点模块（记忆、存储、跨进程调用）必须 100% 覆盖，不能只抽样。

### 4.2 六步探测链（严格单步，每步等结果）

#### 步骤A：真实调用探测

- 用启动参数执行命令，捕获完整 stdout/stderr/退出码。
- 记录关键变量当前值（如记忆数量、记录 ID、状态字段）。

#### 步骤B：日志溯源

- 调取 EXE 运行日志（当前时间点前后至少 50 行）。
- 检查关键字：WARNING、ERROR、Exception、timeout、permission。
- 确认目标模块（如记忆模块）是否有对应的写入/读取日志。

#### 步骤C：依赖状态检查

- 存储文件/数据库：是否存在、是否可读写、磁盘是否已满。
- 缓存（如有）：是否可访问。
- 权限：执行用户对存储目录是否有读写权限。
- 跨进程：bash 沙箱/外部进程是否能调用到该功能。

#### 步骤D：代码级注入追踪（最关键）

- 检查启动参数分支：是否真的进入了目标业务函数，而不是只打印了提示文本。
- 检查条件判断：是否有分支导致业务逻辑被跳过（例如参数校验失败但仍返回成功）。
- 开发环境可插入调试语句或开启 debug 模式，捕获完整调用栈。
- **重点确认**：控制台输出的「写入成功」是否对应真实的存储写入动作。

#### 步骤E：双重验证

用**两种不同方式**获取同一数据，对比结果：

| 操作 | 方式1（EXE 命令） | 方式2（直接查底层） |
|---|---|---|
| 写记忆后验证 | `--list-memory` 看数量 | 直接读取存储文件/SQLite，查记录是否存在 |
| 删记忆后验证 | `--read-memory key` 看是否空 | 直接查存储文件，记录是否已删除 |
| 统计验证 | `--count-memory` 返回数字 | 直接 `wc -l` / SQL COUNT 对比 |

- 两种方式结果**必须一致**，不一致则判定为「静默失败」。

#### 步骤F：持久化校验（涉及存储的命令必须做）

1. 执行写入操作。
2. 完全关闭 EXE，重新启动。
3. 再次执行读取/统计命令。
4. 验证数据**重启后仍然存在**。
5. 若重启后数据消失 → 判定为「仅内存缓存，未持久化」，验收不通过。

### 4.3 归因输出（每步结束后强制结构化反馈）

```
【当前步骤】：A/B/C/D/E/F
【执行的命令/操作】：
【真实输出（完整）】：
【退出码/状态】：
【关键变量当前值】：
【这一步揭示了什么】：
【是否通过】：是 / 否（不通过说明原因）
```

六步全部完成后，输出最终归因：

```
【根因分类】：配置错误 / 权限问题 / 依赖故障 / 代码逻辑 / 持久化未实现 / 跨进程不可用 / 数据真实为空
【证据链】：步骤X发现了什么 → 步骤Y确认了什么
【结论】：业务真实生效 / 静默失败（调用成功但业务未执行）
【是否通过验收】：是 / 否
```

### 4.4 通过标准（全部满足才算通过）

1. 返回值真实来自实际执行，非模拟。
2. 关键变量（ID、count、status）已追溯到底层存储源头。
3. 代码路径至少探查三层：入口 → 中间层 → 数据层。
4. 日志已翻阅当前时间点前后 50 行。
5. 双重验证两种方式结果一致。
6. 涉及存储的命令，持久化校验通过（重启后数据保留）。
7. 归因报告结论为「业务真实生效」。

### 4.5 失败处理

- 能自动定位根因并修复的（如分支逻辑错误、持久化未实现），修改代码后重跑本层。
- 遇到权限问题 → 不直接失败，**升级到第3层权限绕行**。
- 遇到无法自动判定的「体感不适」「词不达意」→ 升级到第4层分片复测。
- 前三层都无法解决 → 才升级到第5层用户介入。

## 五、第3层：权限绕行（自动逐级容错）

> 目标：遇到 Permission denied / EACCES / 403 时，自动尝试绕行，不卡死、不直接放弃。
> 按优先级逐级尝试，前一级成功就不往下走。

### 5.1 第一级：参数绕过（最优先，全自动）

| 场景 | 尝试参数 |
|---|---|
| 用户态绕过 | `--user`、`-u` 指定当前用户 |
| 沙箱/容器 | `--no-sandbox`（仅限开发测试）、`--allow-root` |
| 文件覆盖 | `-f`、`--force` 强制覆盖 |
| 目录创建 | `-p` 自动创建父目录 |
| 端口冲突 | `--port 0` 自动分配空闲端口，或 `--bind 127.0.0.1` |
| 环境变量 | `PYTHONUNBUFFERED=1`、`DEBIAN_FRONTEND=noninteractive` |

### 5.2 第二级：降级到用户目录（全自动）

- 系统目录（/etc、/var、/usr）写入失败时，立即重定向到：
  - `~/.config/xxx/`（配置）
  - `~/logs/xxx.log`（日志）
  - `~/data/xxx.db`（数据）
  - `/tmp/项目名_随机数/`（临时文件）
- 告知：「已降级到用户目录，功能与系统目录一致」。

### 5.3 第三级：sudo 非交互提权（半自动）

- 先检查：`sudo -n true` 是否可用（当前用户是否有 NOPASSWD sudo）。
- 可用则执行 `sudo -n 命令`。
- 不可用则**不卡住**，直接升级到第四级。

### 5.4 第四级：升级到第5层用户介入

- 前三级全部失败时，才输出手工验证桥接，让用户介入。
- **禁止在权限问题上停留超过 3 次尝试而不降级。**

---

## 六、第4层：分片复测（多窗口并行，半自动）

> 目标：抓前三层抓不到的隐性问题——「词不达意」「交互体感差」「边界参数不适」。
> 300+ 命令全部丢给一个 AI 窗口会导致信息过载罢工，必须分片。

### 6.1 分片规则

- 将全部 MCP 函数 + 斜杠命令按**模块/功能域**分组。
- 每份交接文档只包含 **5~15 条命令**（确保单个 AI 窗口能处理完）。
- 文档数量 = 总命令数 ÷ 每片命令数，向上取整。

### 6.2 每份交接文档的结构

```markdown
# MCP 命令测试交接文档 - 分片 N（共 M 片）

## 说明
- 请新开独立 AI 会话处理本文档。
- 每次只执行 1 条命令，通过 EXE 启动参数真实运行。
- 不查阅源码，模拟外部 AI 调用行为。
- 遇到任何异常、模糊、词不达意、空输出、崩溃，记录并修复。
- 耗时 > 30s 的功能会标记 ⏱ 耗时提示。

## 待测试命令列表
1. mcp_xxx_1（模块：记忆）
2. mcp_xxx_2（模块：记忆）
3. slash_cmd_xxx（模块：系统）
...

## 每条命令的测试记录模板
【命令标识】：
【执行启动参数】：
【完整 stdout/stderr】：
【退出码】：
【故障分类】：1崩溃 / 2格式错误 / 3Error:true / 4空输出 / 5超时死锁 / 6词不达意 / 7跨进程不可用 / 8可交付成功
【现象描述】：
【根因分析】：
【修复方案】：
【是否修复完成】：是/否
【耗时备注】：>30s 需填写
【验收结论】：可交付 / 待修复
```

### 6.3 测试要求（站在客户角度）

- **你既是设计者也是使用者**，每条命令都要问：客户看到这个输出会困惑吗？
- 边缘参数必须测：空输入、超长输入、特殊字符、重复操作。
- 「词不达意」判定：命令名承诺的功能，输出是否真的完成了？例如 `memory_write` 输出成功，但 `memory_list` 数量没变 → 词不达意。
- 只要有任何不适，就修改代码做**面向笨蛋客户的宽容兼容**，而不是要求客户改变用法。

### 6.4 通过标准

- 分片内所有命令的验收结论均为「可交付」。
- 所有发现的问题已修复并重测通过。
- 耗时 > 30s 的功能已全部备注。

## 七、第5层：用户介入（最后防线）

> 目标：只有当前四层都无法自动解决时，才让用户动手。
> 用户介入时，必须给出**明确的可执行步骤**，不能只说「权限不足请解决」。

### 7.1 触发条件（满足任一）

- 第3层权限绕行三级全部失败。
- 第2层探测发现需要用户环境信息（如特定配置、账号凭证）。
- 第4层复测发现需要用户主观确认的体验问题。
- 任何自动修复尝试超过 3 次仍失败。

### 7.2 手工验证桥接格式（强制）

```
【自动执行状态】：失败
【失败原因】：权限不足 / 环境缺失 / 需用户确认（具体说明）
【已尝试的自动方案】：
  - 参数绕过：已尝试 --force、--no-sandbox，无效
  - 降级用户目录：应用不支持用户目录运行
  - sudo -n 提权：当前用户无 NOPASSWD sudo 权限

【请执行以下命令，并将输出粘贴回来】：
```bash
# 命令1：检查目标权限
ls -la /path/to/target

# 命令2：手动执行（可能需要 sudo）
sudo bash -c "具体命令"

# 命令3：检查当前用户组
id
```

【验证后分支】：
· 手工执行成功 → 将输出粘贴给我，我继续后续步骤
· 手工执行失败 → 我提供替代方案或跳过该步骤并记录风险
```

### 7.3 禁止项

- ❌ 禁止输出「权限不足，任务终止」后不做任何引导。
- ❌ 禁止让用户去「自己解决一下」而不给出具体命令。
- ❌ 禁止在用户介入后不接管后续流程——用户粘贴结果后必须自动继续。

## 八、8 类故障与防御层映射

| 故障编号 | 现象 | 首次拦截层 | 最终兜底层 |
|---|---|---|---|
| 1 | 直接崩溃、边缘参数崩溃 | 第1层 快速扫描 | 第0层 修复代码做输入防护 |
| 2 | 输入输出格式错误 | 第1层 快速扫描 | 第0层 统一返回结构 |
| 3 | 格式对了但 `error:true` | 第1层 快速扫描 | 第2层 日志溯源定位根因 |
| 4 | `error:false` 但空输出 | 第1层 快速扫描 | 第0层 强制 message 非空 |
| 5 | 超时、死锁 | 第1层 耗时检测 | 第2层 代码追踪，改用 Actor 管道模式 |
| 6 | 词不达意（业务没执行） | 第2层 穿透探测 | 第4层 客户视角复测确认 |
| 7 | 跨进程/沙箱不可用 | 第2层 依赖检查 | 第0层 修复持久化/跨进程逻辑 |
| 8 | 真正成功可交付 | 第2层 双重验证通过 | 第4层 分片复测最终确认 |

## 九、全局验收通过门槛（交付前最终检查）

全部满足才能宣布交付：

1. **第1层**：300+ MCP 函数、全部斜杠命令表层扫描通过，无崩溃、无格式错误。
2. **第2层**：重点模块（记忆、存储、跨进程）100% 穿透探测通过；其余模块抽样覆盖率 ≥ 30%。
3. **第3层**：所有权限问题已自动绕行或修复，无未解决的 Permission denied。
4. **第4层**：全部分片交接文档完成复测，所有命令验收结论为「可交付」。
5. **持久化**：所有涉及存储的命令，重启后数据保留验证通过。
6. **跨进程**：bash 沙箱/外部进程可调用，不依赖 JCC 内部环境。
7. **耗时**：所有 > 30s 的功能已在返回值和文档中备注。
8. **统一格式**：启动参数格式、返回值结构全局统一，无歧义特例。
9. **零「设计限制」**：不存在以「设计限制」为由未实现的功能——用不了就是 bug。

## 十、执行流程总结（一图流）

```
开始
  │
  ▼
第0层：统一参数格式 + 统一返回结构（写代码时完成）
  │
  ▼
第1层：脚本批量扫描全部命令
  │
  ├─ 崩溃/格式错/Error:true/空输出/超时 → 记录坏点 → 修复代码 → 重跑第1层
  │
  ▼ 表层全部通过
第2层：随机抽样 + 重点模块全覆盖，六步穿透探测
  │
  ├─ 权限问题 → 第3层自动绕行 → 成功则回到第2层继续
  ├─ 词不达意/静默失败 → 修复代码 → 重跑第2层
  ├─ 持久化未实现/跨进程不可用 → 修复代码 → 重跑第2层
  │
  ▼ 穿透探测通过
第4层：全量命令分片，多 AI 窗口并行客户视角复测
  │
  ├─ 发现体感问题/边界不适 → 修复代码 → 重测该分片
  │
  ▼ 全部分片可交付
第5层：仅当前四层有未解决项时，输出手工验证桥接让用户介入
  │
  ▼ 用户反馈后自动继续
最终交付检查（第九条全部满足）
  │
  ▼
交付完成
```

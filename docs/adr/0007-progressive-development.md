# 0007. 渐进式开发方法

- 状态：accepted
- 日期：2026-08-29
- 决策者：项目架构组

## 背景

大型任务一次性完成易堆积错误到末尾，难以定位；中途中断无法恢复；缺乏可验证的中间产物。需要一种持续推进、每步可验证的工作方式。

## 决策

**渐进式 = 每完成一个关键步骤就自动执行 `编译 → 测试 → commit`，持续推进，不中断、不等待、不询问。**

核心要求：
1. 每次只完成一个功能，编译，单元测试，git 提交
2. 主工程编译成功后，测试用例也需编译成功
3. 一旦有疑问或发现错误，**立即停止**，先修复再继续
4. **禁止中途暂停询问用户"是否继续"** — 用户可随时中断，不需要 AI 提醒

核心目的：
- ① 每步都有可验证的产物（编译产物/测试结果/git 提交）
- ② 任何时刻中断都能从最近的 commit 恢复
- ③ 错误在萌芽阶段就被捕获，而非堆积到末尾

任务失败处理：
- 总上限 3 次重试（含自行修复和回滚重试）
- 降级策略：错误累积过多时拆成更小的子步骤（单文件单函数级别），禁止整体回滚重试

## 替代方案

1. **一次性完成再验证**：放弃。错误堆积到末尾，定位困难；中断无法恢复。
2. **每步询问用户是否继续**：放弃。违反"用户可随时中断"原则，且打断流。
3. **只编译不提交，最后统一提交**：放弃。中断无法恢复，违反渐进式核心目的②。

## 后果

- 正面：错误早捕获、中断可恢复、每步有产物
- 负面：commit 频率高，历史提交多（但 squash 合并 PR 后 main 只留一个提交，可接受）
- 中性：每完成一个功能点并编译成功后，记录 `<!-- 🤖 Auto Decision -->` 注释到工作文件末尾

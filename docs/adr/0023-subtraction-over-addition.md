# 0023. 减法思维优先

- 状态：accepted
- 日期：2026-08-29
- 决策者：项目架构组

## 背景

解决问题时倾向"加新特性/新层/新策略"（加法思维），看似安全，实际增加复杂度。如：加 `[DoNotAutoRegister]` 特性阻止 DI 注册、加 ShellCapabilityProvider DI 单例只为首次检测缓存、加 FileShare 降级策略层。

## 决策

**减法思维优先：去掉不必要的中间层，而非加新层。**

反例（禁止）→ 正例（正确）：

| ❌ 加法思维 | ✅ 减法思维 |
|------------|------------|
| 加 `[DoNotAutoRegister]` 新特性阻止 DI 注册 | 减少不必要的 DI 暴露（如 ShellProviderBase 不需要 IShellProvider） |
| 加 ShellCapabilityProvider DI 单例只为首次检测缓存 | 用静态 ShellCapabilityCache，启动时检测一次 |
| 加 FileShare 降级策略层 | 用 FileShare.ReadWrite + Named Mutex 一步到位 |

**根因**：加新特性/新层/新策略看似"安全"，实际增加复杂度。减法才是正道——去掉不必要的中间层。

## 替代方案

1. **始终用加法思维**：放弃。复杂度累积，系统臃肿，维护成本高。
2. **按情况选择加法/减法**：放弃。默认减法，加法需充分理由，否则倾向减法。
3. **一次性全量减法重构**：禁止。违反渐进式（见 ADR 0007），风险高。

## 后果

- 正面：复杂度不累积；系统精简；维护成本低
- 负面：减法重构需深入理解现有代码，初期成本高
- 中性：加法在充分理由下仍可使用（如新功能、新抽象），但默认倾向减法

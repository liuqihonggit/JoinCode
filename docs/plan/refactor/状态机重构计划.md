> 生成时间：2026-08-23

**路径**：`infrastructure/Infrastructure/Utils/State/StateMachine.cs:10`

public sealed class TaskStateMachine

        _stateMachine.StateChanged += OnStateChanged;

    public event EventHandler<StateChangedEventArgs<TaskState>>? StateChanged;
    public bool TryTransitionTo(TaskState target) => _stateMachine.TryTransitionTo(target);
    // ... 转发其他方法

    private static FrozenDictionary<TaskState, FrozenSet<TaskState>> CreateTransitionTable() => ...
}

## 三、第一梯队详细设计方案

### 候选 B6：`TaskRuntime.UpdateTaskAsync` 加转换验证

**当前问题**（`core/execution/Scheduling/src/Runtime/TaskRuntime.cs:71-100`）：
```csharp
if (update.Status is not null) task.Status = update.Status.Value;  // 行 81 — 无验证直接赋值
```
已有 `TaskStateMachine` 可复用却未使用，允许任意状态跳跃（如 `Completed → Pending` 非法但代码允许）。

**设计方案**：
1. `RuntimeTask` 内嵌一个 `TaskStateMachine`（按需创建，懒加载）
2. `UpdateTaskAsync` 中状态变更走 `TryTransitionTo`，失败返回 `OperationResult.Fail`
3. 保留 `ForceTransitionTo` 用于崩溃恢复路径（`RecoverTasksAsync` 行 353 `Running → Pending` 是合法恢复，需在转换表中显式添加）

**状态转换图**（复用 `TaskStateMachine` 现有表 + 恢复转换）：
```
Pending → WaitingForDependencies | InProgress | Cancelled
WaitingForDependencies → InProgress | Cancelled
InProgress → Paused | Completed | Failed | Stopped
Paused → InProgress | Cancelled
Completed → InProgress (重试) | Pending (恢复)   ← 新增恢复转换
Failed → InProgress (重试) | Pending (恢复) | Cancelled   ← 新增恢复转换
Cancelled → Pending (恢复)   ← 新增恢复转换
Stopped → Pending (恢复)   ← 新增恢复转换
```

**接口变更**：
- `RuntimeTask` 新增 `internal TaskStateMachine StateMachine { get; }`（懒加载，初始状态 = `Status` 映射到 `TaskState`）
- `UpdateTaskAsync` 签名不变，但失败时返回 `Fail("非法状态转换: {old} → {new}")`
- `TaskState` 与 `TaskExecutionStatus` 的映射函数（两个枚举状态不完全一致，需确认映射关系）

**重构步骤**：
1. 🔴 写单元测试：`UpdateTaskAsync` 从 `Completed` 转 `Pending` 应失败（除非是恢复路径）
2. 🔴 写单元测试：`RecoverTasksAsync` 中 `Running → Pending` 应成功
3. 🟢 在 `TaskStateMachine` 转换表添加恢复转换
4. 🟢 `RuntimeTask` 添加 `StateMachine` 属性
5. 🟢 `UpdateTaskAsync` 改用 `TryTransitionTo`
6. 🟢 `RecoverTasksAsync` 用 `ForceTransitionTo` 跳过验证（恢复场景）
7. 编译 + 测试 + 提交

**风险**：`TaskState` 与 `TaskExecutionStatus` 是两个不同枚举，需确认是否合并或建立映射。`TaskExecutionStatus` 有 `Ready/WaitingForDependency`，`TaskState` 有 `WaitingForDependencies/InProgress`，命名不一致。

### 候选 C2：`BridgeStatusUtil.GetBridgeStatus` 消除 bool 参数

**当前问题**（`services/Bridge/src/Core/BridgeStatusUtil.cs:127-150`）：
```csharp
public static BridgeStatusInfo GetBridgeStatus(bool error, bool connected, bool sessionActive, bool reconnecting)
```
4 个 bool 参数有 16 种组合，但合法状态仅 5 种。同文件已有 `BridgeStatusState` 枚举（Idle/Attached/Titled/Reconnecting/Failed）却未在此方法使用，**重复表达**。

**设计方案**：
1. 新增 `GetBridgeStatus(BridgeStatusState state)` 重载，用 switch 表达式映射到 `BridgeStatusInfo`
2. 旧 4-bool 方法标记 `[Obsolete]`，内部转换为 `BridgeStatusState` 后调用新方法
3. 查找所有调用方，迁移到新方法

**状态映射**：
```
Failed     → { Label="Bridge Error",     Color="error" }
Reconnecting → { Label="Reconnecting",   Color="warning" }
Idle       → { Label="Disconnected",    Color="error" }   // 注意：原代码 !connected → Disconnected
Attached   → { Label="Connected",       Color="success" }
Titled     → { Label="Active",          Color="success" } // sessionActive → Active
```

**bool → 枚举推导规则**（旧方法内部转换）：
```
error=true        → Failed
reconnecting=true → Reconnecting
connected=false   → Idle
sessionActive=true → Titled
else              → Attached
```

**接口变更**：
- 新增 `public static BridgeStatusInfo GetBridgeStatus(BridgeStatusState state)`
- 旧方法 `[Obsolete("使用 GetBridgeStatus(BridgeStatusState) 替代")]`

**重构步骤**：
1. 🔴 写单元测试：新方法对 5 个枚举值返回正确 `BridgeStatusInfo`
2. 🔴 写单元测试：旧方法行为不变（兼容）
3. 🟢 实现新方法
4. 🟢 旧方法标记 `[Obsolete]` 并委托新方法
5. 查找调用方（`grep "GetBridgeStatus"`），逐一迁移
6. 编译 + 测试 + 提交

**风险**：`BridgeStatusState.Titled` 在原 `GetBridgeStatus` 中未使用（原代码 `sessionActive → Active`，而枚举叫 `Titled`），需确认语义。可能 `Titled` 是给"有标题的会话"用，`Attached` 是"已连接无会话"，需查 TS 端对齐。

### 候选 A3+A4：熔断器统一

**当前问题**：
- A3 `infrastructure/Transport.Impl/src/Shared/TransportCircuitBreaker.cs:3` — `CircuitBreakerState`（Closed/Open/HalfOpen），无锁
- A4 `infrastructure/Infrastructure/Utils/Resilience/UnifiedCircuitBreaker.cs:10` — `CircuitBreakerPhase`（Closed/Open/HalfOpen），有锁 + 更多计数器

**两套重复实现**，枚举名不同，A4 功能更全（`HalfOpenMaxProbe`/`TotalFailures`/`LastFailureTime`/`Reset`）。

**设计方案**：
1. 保留 A4 `UnifiedCircuitBreaker` 作为唯一实现（功能更全）
2. A3 `TransportCircuitBreaker` 标记 `[Obsolete]`，内部委托 `UnifiedCircuitBreaker`
3. 查找 A3 调用方，迁移到 A4
4. 统一枚举为 `CircuitBreakerPhase`（删除 `CircuitBreakerState`）
5. **不强行用 `StateMachine<TState>`**：熔断器的 `Open → HalfOpen` 是**时间驱动**（冷却期到期自动转换），不是显式 `TransitionTo` 调用，`StateMachine<TState>` 的转换表模型不适合。保持手写但统一到一套。

**状态转换图**（时间驱动）：
```
Closed → Open (连续失败 ≥ 阈值)
Open → HalfOpen (冷却期到期， GetCurrentPhase 自动转换)
HalfOpen → Closed (探测成功)
HalfOpen → Open (探测失败)
```

**接口变更**：
- 删除 `CircuitBreakerState` 枚举
- `TransportCircuitBreaker` 标记 `[Obsolete]`，委托 `UnifiedCircuitBreaker`
- 调用方迁移到 `UnifiedCircuitBreaker`

**重构步骤**：
1. 🔴 写单元测试：`UnifiedCircuitBreaker` 行为覆盖 A3 所有场景
2. 🟢 `TransportCircuitBreaker` 内部委托 `UnifiedCircuitBreaker`
3. 🟢 标记 `[Obsolete]`
4. 查找 A3 调用方，逐一迁移
5. 编译 + 测试 + 提交

**风险**：A3 无锁，A4 有锁，性能差异需评估（A3 在 Transport 热路径）。

# 万物皆插件迁移计划

> 基于 DSH(DeepSeek Harness) "一切皆插件" 理念,将项目内部硬编码实现逐渐改为插件
> ADR: [0098](../../adr/0098-plugin-system-fusion-actor-effectscope.md)
> 创建: 2026-09-11

## 一、DSH 万物皆插件理念

DSH(DeepSeek Harness) 是 DeepSeek 开源的 coding/自动化 agent,核心理念:

> **核心只留循环与抽象缝(Seam),能力全靠插件组合**

| 概念 | 说明 | 本项目对应 |
|------|------|-----------|
| **AgentLoop** | 唯一核心循环 | 已有(非插件化目标) |
| **Seam(能力缝)** | `ctx.llm`/`ctx.tools`/`ctx.sandbox` 等抽象接口 | 已有大量接口(`IQueryService`/`IToolHandler`/`ISandboxProvider`) |
| **Cordis 底座** | Context/服务注入/插件装载框架 | `PluginContext` + `PluginManager` + DI |
| **Plugin** | `apply(ctx, config)` 或 class + 清单声明 | `IWorkflowPlugin` + `WorkflowPluginBase` |
| **inject** | 静态声明依赖,capability-based 安全 | `PluginContext.RegisterService<T>` |
| **Profile** | 插件组合配置 | 待建(当前用 `settings.json` + DI) |
| **Bundle** | 自带 patch 的插件包 | 待建 |

### DSH 插件形态

```
① 函数式: apply(ctx, config) — 挂工具/监听事件,无状态
② 类式: class extends Service — 提供服务能力
```

本项目对应: `IWorkflowPlugin.LoadAsync(PluginContext)` + `InitializeAsync(IServiceProvider)` + `Unload()`

### 业务插件: 零

**整个项目没有任何类实现 `IWorkflowPlugin` 接口。** 10 个能力模块全部通过 `[Register]` 特性 + 源码生成器在编译时静态注册。

## 五、迁移步骤模板

每个能力模块的迁移遵循统一步骤:

### 步骤1: 定义插件契约

```csharp
public sealed class XxxPlugin : WorkflowPluginBase
{
    public XxxPlugin() : base("xxx-plugin") { }

    public override Task<OperationResult> LoadAsync(PluginContext ctx, CancellationToken ct)
    {
        // 1. 声明依赖(inject)
        ctx.DeclareDependency("core-plugin");

        // 2. 注册服务/工具
        ctx.RegisterService<IXxxService>(new XxxServiceImpl());

        // 3. 副作用撤销链
        ctx.Effect(
            apply: () => RegisterSomething(),
            revert: () => UnregisterSomething(),
            desc: "注册 Xxx 能力");

        return Task.FromResult(OperationResult.Ok());
    }

    public override Task<OperationResult> InitializeAsync(IServiceProvider sp, CancellationToken ct)
    {
        // 从 sp 获取依赖服务,完成初始化
        return Task.FromResult(OperationResult.Ok());
    }

    public override OperationResult Unload()
    {
        // 清理资源(EffectScope 自动撤销)
        return OperationResult.Ok();
    }
}
```

### 步骤2: 编写单元测试

- 测试 `LoadAsync` 正确注册服务
- 测试 `Unload` 正确撤销所有副作用
- 测试 `ValidateUnloadContract` 通过

### 步骤3: 编写 E2E 测试

- 通过 `IPluginManager.LoadPluginAsync` 加载插件
- 验证能力可用
- 通过 `IPluginManager.UnloadPluginAsync` 卸载
- 验证 ALC 回收 + 资源释放

### 步骤4: 替换硬编码注册

```csharp
// 旧: ServiceRegistration.AddXxxServices(services)
// 新: pluginManager.LoadPluginAsync(new XxxPlugin(), ct)
```

### 步骤5: 验证无回归

- 全量编译
- 全量测试
- 手动 exe 验证

## 六、风险与注意事项

### 风险1: NativeAOT 兼容

- 插件 DLL 必须标记 `IsAotCompatible`
- 禁止 `dynamic`、反射 emit、`DispatchProxy`
- JSON 序列化用 `JsonContext` + 源码生成器

### 风险2: ALC 卸载泄漏

- 插件中所有资源必须通过 `ctx.Effect` 注册撤销
- 后台任务必须用 `ctx.RunBackgroundTask` 而非裸 `Task.Run`
- 事件订阅必须用 `ctx.WeakSubscribe` 而非原生 `+=`

### 风险3: 依赖循环

- 用 `PluginDependencyGraph` 检测循环
- 用 `DeclareDependency` 声明插件间依赖
- 连带卸载: 卸载 A → 自动卸载依赖 A 的 B

### 风险4: 性能

- 插件加载/卸载有 ALC 开销
- 热路径不应频繁加载/卸载
- 一次性加载 + 长期运行是推荐模式

### 风险5: 渐进式迁移

- 禁止一次性迁移所有模块
- 每次只迁移一个模块,编译+测试+提交
- 保留旧硬编码路径直到插件路径验证通过

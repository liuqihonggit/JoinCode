## 1. P0 紧急 — 规则 ID 冲突（Bug）✅ 已完成

### 1.1 问题描述

`JCC4001`/`JCC4002`/`JCC4003` 在两个分析器中重复定义，且严重级别冲突：

| 规则 ID | 位置 A（并发规则） | 位置 B（DI 注册规则） | 冲突 |
|---------|-------------------|---------------------|------|
| JCC4001 | `ConcurrencyRules.cs:25` Warning: lock 在 async 方法 | `RegisterAttributeAnalyzer.cs:18` **Error**: [Register] 多接口缺显式类型 | Warning vs Error |
| JCC4002 | `ConcurrencyRules.cs:34` Warning: SemaphoreSlim.Wait 无超时 | `ServiceRegistrationGenerator.cs:13` **Error**: DI 循环依赖 | Warning vs Error |
| JCC4003 | `ConcurrencyRules.cs:43` Warning: lock 内 GetAwaiter | `RegisterAttributeAnalyzer.cs:27` **Error**: [Register] 必须继承 ServiceEntity | Warning vs Error |

### 1.2 影响

- `dotnet build --filter JCC4001` 无法区分是死锁警告还是 DI 注册错误
- IDE 灯泡提示合并，修复建议混乱
- `AnalyzerReleases.Shipped.md` 中同一 ID 对应两个不同描述
- 严重级别不一致：Roslyn 会加载两个 descriptor，Error 级别会阻断编译，但 Warning 级别的诊断也会同时报告

### 1.3 修复方案

**策略**: 保留并发规则的 JCC4001/4002/4003（历史已发布），将 DI 注册规则迁移到新 ID。

| 旧 ID | 新 ID | 描述 |
|-------|-------|------|
| JCC4001 (DI) | **JCC4010** | [Register] 多接口缺显式类型 |
| JCC4002 (DI) | **JCC4011** | DI 循环依赖 |
| JCC4003 (DI) | **JCC4012** | [Register] 必须继承 ServiceEntity |

**改动文件**:

| 文件 | 改动 |
|------|------|
| `generators/McpToolDispatch.Generator/src/RegisterAttributeAnalyzer.cs:18` | `"JCC4001"` → `"JCC4010"` |
| `generators/McpToolDispatch.Generator/src/RegisterAttributeAnalyzer.cs:27` | `"JCC4003"` → `"JCC4012"` |
| `generators/McpToolDispatch.Generator/src/ServiceRegistrationGenerator.cs:13` | `"JCC4002"` → `"JCC4011"` |
| `generators/McpToolDispatch.Generator/src/AnalyzerReleases.Shipped.md` | 更新规则 ID 映射 |
| `generators/AotSafety.Generator/src/AnalyzerReleases.Shipped.md` | 确认无 JCC4010-4012 冲突 |

**验证**:

### 1.4 风险

- **低**: 分析器规则 ID 变更不影响已编译的代码，只影响诊断输出

## 2. P1 高 — IToolExecutionGateway 双重注册 ✅ 已完成

### 2.1 问题描述

`PermissionAwareToolExecutor` 同时通过两种方式注册到 `IToolExecutionGateway`：

```csharp
// 方式1: 裸 [Register] 自动发现（core/execution/McpToolDispatch/.../PermissionAwareToolExecutor.cs:9）
[Register]
public sealed partial class PermissionAwareToolExecutor : ServiceEntity, IToolExecutionGateway
```

```csharp
// 方式2: 手动转发注册（composition/Composition/.../ServiceRegistration.Mcp.cs:80）
services.AddSingleton<IToolExecutionGateway>(sp => sp.GetRequiredService<PermissionAwareToolExecutor>());
```

### 2.2 影响

- 双注册点：`[Register]` 自动注册 + 手动 `AddSingleton` 转发
- 后注册 wins，若顺序变化可能导致行为不一致
- 维护负担：修改 `PermissionAwareToolExecutor` 构造函数需同步检查两处注册
- 注释已标注"[Register] 自动注册"，说明开发者知晓但未消除冗余

### 2.3 修复方案

**策略**: 改为显式 `[Register(typeof(IToolExecutionGateway))]`，删除手动转发。

**改动文件**:

| 文件 | 改动 |
|------|------|
| `core/execution/McpToolDispatch/src/Core/Execution/PermissionAwareToolExecutor.cs:9` | `[Register]` → `[Register(typeof(IToolExecutionGateway))]` |
| `composition/Composition/src/DependencyInjection/Infrastructure/ServiceRegistration.Mcp.cs:79-80` | 删除手动转发行及注释 |

**验证**:
```powershell
dotnet build core/execution/McpToolDispatch/src/McpToolDispatch.csproj -c Debug
dotnet build composition/Composition/src/Composition.csproj -c Debug
dotnet test tests/Unit/ --filter "Category!=Integration" --filter "ToolExecution"
```

### 2.4 风险

- **低**: `IToolExecutionGateway` 只有 `PermissionAwareToolExecutor` 一个实现，改为显式注册语义不变
- 需确认 `[Register(typeof(...))]` 生成器输出的注册代码与手动转发行为一致（Singleton 生命周期）

## 3. P1 高 — 反射 API 分析器缺失（JCC1007）✅ 已完成

### 3.1 问题描述

`JCC1004`（Error）检测了 `dynamic` 关键字，但未检测其他 AOT 不兼容的反射 API：

| 危险 API | 当前检测 | NativeAOT 影响 |
|---------|---------|---------------|
| `System.Reflection.Emit.*` | ❌ 未检测 | 运行期生成 IL，AOT 不支持 |
| `Assembly.Load / Assembly.LoadFrom` | ❌ 未检测 | 运行期加载程序集，AOT 裁剪后可能不存在 |
| `Type.GetType(string)` | ❌ 未检测 | 运行期类型解析，AOT 裁剪后可能失败 |
| `Activator.CreateInstance(Type)` | ❌ 未检测 | 运行期实例化，AOT 需要预注册 |
| `MethodInfo.Invoke` | ❌ 未检测 | 运行期反射调用，AOT 性能差 |

### 3.2 修复方案

**策略**: 在 `AotSafetyRules.cs` 新增 5 条规则 JCC1007-JCC1011（注意 JCC1011/1012 已被 JsonSerializerAotRules 占用，改用 JCC1013-1016）。

**新增规则**:

| 规则 ID | 严重级别 | 检测目标 | 建议替代 |
|--------|---------|---------|---------|
| JCC1007 | Error | `Reflection.Emit.*` | 源码生成器编译期生成 |
| JCC1013 | Warning | `Assembly.Load*` | 静态引用 + Trimmer 根 |
| JCC1014 | Warning | `Type.GetType(string)` | `typeof(T)` 编译期已知 |
| JCC1015 | Warning | `Activator.CreateInstance(Type)` | `new T()` 或工厂模式 |
| JCC1016 | Warning | `MethodInfo.Invoke` | 直接调用或源码生成器分发 |

**改动文件**:

| 文件 | 改动 |
|------|------|
| `generators/AotSafety.Generator/src/AotSafetyRules.cs` | 新增 5 个 DiagnosticDescriptor + AnalyzeNode 逻辑 |
| `generators/AotSafety.Generator/src/AnalyzerReleases.Unshipped.md` | 新增 JCC1007/1013-1016 条目 |

**验证**:
```powershell

dotnet build Generators.slnx -c Debug --no-incremental
# 全量编译确认无误报
```

### 3.3 风险

## 4. P2 中 — 层间引用分析器（"大树生长"核心护栏）✅ 已完成

### 4.1 问题描述

AGENTS.md 定义了七层架构（Generators → Foundation → Infrastructure → Core → Services → Composition → App），但**无编译期强制**。当前依赖人工遵守，存在退化风险：

| 违规场景 | 当前检测 | 后果 |
|---------|---------|------|
| App 直接引用 Generators | ❌ 未检测 | 绕过生成器隔离 |
| Core 引用 Services | ❌ 未检测 | 反向依赖，循环编译 |
| Foundation 引用 Infrastructure | ❌ 未检测 | 抽象依赖实现 |

### 4.2 修复方案

**策略**: 新增 `LayerDependencyAnalyzer` 分析器，基于项目名称前缀推断所属层，检测 ProjectReference 违规。

**层推断规则**（基于 csproj 路径或 AssemblyName）:

| 路径前缀 | 层 | 允许引用的下层 |
|---------|---|--------------|
| `generators/` | 0-Generators | （无） |
| `foundation/` | 1-Foundation | 0-Generators |
| `infrastructure/` | 2-Infrastructure | 1-Foundation |
| `core/` | 3-Core | 1-Foundation, 2-Infrastructure |
| `services/` | 4-Services | 1-Foundation, 2-Infrastructure, 3-Core |
| `composition/` | 5-Composition | 1-Foundation, 2-Infrastructure, 3-Core, 4-Services |
| `app/` | 6-App | 1-Foundation, 2-Infrastructure, 3-Core, 4-Services, 5-Composition |

**新增规则**:

| 规则 ID | 严重级别 | 描述 |
|--------|---------|------|
| JCC11001 | Error | 层间违规引用：{SourceLayer} 不允许引用 {TargetLayer} |
| JCC11002 | Warning | 跳层引用：{SourceLayer} 引用 {TargetLayer} 跳过了 {SkippedLayer}（建议通过中间层聚合） |

**实现挑战**:
- Roslyn 分析器在单个编译内运行，无法直接访问 ProjectReference 图
- 方案 A: 分析 `#r` 指令和 `using` 的程序集名推断依赖（不精确）
- 方案 B: **在 JccAuditAstCli 中实现**（已有 `SlnxParser` 解析 slnx，可构建项目依赖图）— 推荐
- 方案 C: MSBuild 自定义 Task 在编译期检查 csproj 的 ProjectReference

**推荐方案 B**: 在 `tools/JccAuditAstCli` 新增 `layer-audit` 子命令，解析所有 slnx 的 ProjectReference，构建层依赖图，报告违规。

**改动文件**:

| 文件 | 改动 |
|------|------|
| `tools/JccAuditAstCli/.../LayerDependencyAuditor.cs` | 新增：层推断 + 依赖图 + 违规检测 |
| `tools/JccAuditAstCli/.../Program.cs` | 新增 `layer-audit` 子命令入口 |
| `tools/JccAuditAstCli/.../SlnxParser.cs` | 扩展：提取 ProjectReference |

**验证**:
```powershell
dotnet build tools/JccAuditAstCli/JccAuditCli.csproj -c Release
artifacts\bin\JccAuditCli\Release\net10.0\jcc-audit.exe layer-audit
```

### 4.3 风险

- **低**: 作为 CLI 工具而非编译期分析器，不影响编译速度
- 若发现现有违规引用，需逐一审查是否为合理例外（如 `composition/Pipelines` 被 App 引用）

## 5. P2 中 — 统一门面 IRegistryHub ✅ 已完成

### 5.1 问题描述

存在 11 个分散的 Registry 接口，调用方需分别注入：

| Registry 接口 | 定义层 | 消费方 |
|--------------|-------|--------|
| `IToolRegistry` | Foundation | ToolExecutor, ToolRegistryAdapter |
| `IMcpToolRegistry` | Foundation | MCP 服务 |
| `IGoalRegistry` | Foundation | 调度服务 |
| `IDreamTaskRegistry` | Services | Dream 服务 |
| `ISystemActuatorRegistry` | Foundation | 系统执行器 |
| `IAgentRoleRegistry` | Foundation | Agent 协调器 |
| `ICodeIndexerRegistry` | Foundation | 代码索引 |
| `IForegroundTaskRegistry` | Foundation | Shell |
| `IPluginCommandRegistry` | Infrastructure | 插件 |
| `IFileReadListenerRegistry` | Foundation | 文件 IO |
| `IAsyncHookRegistry` | Core | Guard |

### 5.2 修复方案

**策略**: 新增 `IRegistryHub` 聚合门面，提供统一访问入口，**不删除**现有接口（渐进式）。

```csharp
// foundation/Abstractions/00-core/Composition/IRegistryHub.cs
public interface IRegistryHub
{
    IToolRegistry Tools { get; }
    IMcpToolRegistry McpTools { get; }
    IGoalRegistry Goals { get; }
    ISystemActuatorRegistry SystemActuators { get; }
    IAgentRoleRegistry AgentRoles { get; }
    ICodeIndexerRegistry CodeIndexers { get; }
    IForegroundTaskRegistry ForegroundTasks { get; }
    IFileReadListenerRegistry FileReadListeners { get; }
    // 注意: IDreamTaskRegistry/IPluginCommandRegistry/IAsyncHookRegistry 
    // 属于特定层，不聚合到通用 Hub
}
```

**改动文件**:

| 文件 | 改动 |
|------|------|
| `foundation/Abstractions/00-core/Composition/IRegistryHub.cs` | 新增接口 |
| `composition/Composition/src/DependencyInjection/Core/ServiceRegistration.cs` | 注册 `RegistryHub` 实现 |
| 调用方（可选迁移） | 逐步改为注入 `IRegistryHub` 而非单独 Registry |

### 5.3 风险

- **低**: 纯新增接口，不破坏现有代码
- 聚合门面可能成为"上帝接口"，需控制只聚合真正通用的 Registry
- `IDreamTaskRegistry` 等层特有 Registry 不聚合，避免 Hub 依赖 Services 层

## 6. P2 中 — Mcp 服务拆分评估 ✅ 不拆分

### 6.1 问题描述

`services/Mcp/src/` 包含 19 个子模块，是最大的单一服务项目：

```
Auth/ Bridge/ Client/ Communication/ Constants/ Core/ Dev/ McpProtocol/
Models/ Protocol.Contracts/ Remote/ Skill/ Task/ Terminal/ Transports/ User/ Utils/ Workflow/
```

### 6.2 评估结果 — 不拆分

**编译时间测量**（2026-08-12）：

| 模式 | 编译时间 | 阈值 | 结论 |
|------|---------|------|------|
| Debug --no-incremental | 8.6s | 30s | ✅ 远低于阈值 |
| Release --no-incremental | 18.8s | 30s | ✅ 低于阈值 |

**决策: 不拆分**。理由：
1. 编译时间在可接受范围内（Debug 8.6s, Release 18.8s）
2. 拆分会增加编译复杂度（多个 csproj 的依赖管理）
3. 拆分影响所有依赖 Mcp 的上层项目（高风险）
4. 当前单 csproj 结构简单，维护成本低

### 6.3 原评估方案（备选）

**策略**: 评估拆分为 3-4 个 csproj：

| 拆分后项目 | 包含子模块 | 依赖 |
|-----------|-----------|------|
| `Mcp.Core` | Core, Constants, Models, Utils, McpProtocol, Protocol.Contracts | Foundation |
| `Mcp.Transport` | Transports, Communication, Bridge | Mcp.Core |
| `Mcp.Server` | Server, Auth, Remote, Skill, Task, Terminal, User, Workflow, Dev | Mcp.Core, Mcp.Transport |

**注意**: 此项为**评估**项，需先测量当前编译时间和内存占用，判断是否值得拆分。拆分 csproj 会增加编译复杂度。

### 6.3 风险

- **高**: csproj 拆分影响所有依赖 Mcp 的上层项目
- 需更新 `Services.slnx` 和所有引用 Mcp 的 csproj
- 建议先做性能基线测量，若编译时间 < 30s 则不拆分

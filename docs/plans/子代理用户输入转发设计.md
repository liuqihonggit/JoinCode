# 子代理用户输入转发设计

## 目标

启动子代理后，用户仍可向主代理发送消息，主代理将用户意图转发给运行中的子代理。

## 用户决策（已确认）

| 决策点 | 选择 | 说明 |
|--------|------|------|
| 转发触发范围 | **前台 + 后台子代理** | 所有运行中的子代理都可接收用户转发 |
| 输入注入方式 | **缓冲到下轮自然消费** | 消息入队列，子代理每轮 LLM 调用前主动 poll |
| 主代理 LLM 感知 | **主代理 LLM 协同决策** | 用户输入先经主代理 LLM 判断是否转发、如何包装后再发给子代理 |

## 用户修正（2026-08-16）

| 修正 | 说明 |
|------|------|
| **禁止无条件广播** | 用户追加输入不能广播给全部子代理，必须定向转发给单个目标 |
| **`@agentName` 直接注入** | 用户可用 `@agentName 消息` 语法直接指定子代理转发，绕过主代理 LLM 协同决策 |

### `@` 语法路由规则

```
用户输入 → 解析
  ├─ 以 @agentName 开头 → 直接转发给指定子代理（绕过主代理 LLM）
  │   ├─ agentName 匹配运行中子代理 → ForwardUserInputToAgentAsync(agentId, 消息)
  │   └─ agentName 不匹配 → 提示"未找到子代理 xxx，当前运行中: [列表]"
  └─ 不以 @ 开头 → 走主代理 LLM 协同决策（阶段4 UserInputForwardRouter）
      └─ Router 返回单个 targetAgentId（非广播）→ ForwardUserInputToAgentAsync
```

## 实施阶段（渐进式，每阶段编译+测试+提交）

### 阶段1：子代理消息队列消费（缓冲到下轮自然消费）

**目标**：子代理在每轮 LLM 调用前 poll 消息队列，有用户转发消息则追加到 ChatHistory。

**修改**：
1. `AgentMessageTypes.cs` [新] — 定义 `MessageSubType` 常量：`user_forward`、`agent_to_agent`、`permission_response`
2. `AgentBase.ExecuteStreamAsync` (`core/ai/Agents/src/Coordinator/Fork/AgentBase.cs:290`) — 在 LLM 查询前插入 `await DrainPendingUserMessagesAsync(chatHistory, ct)`：
   - 从 `_messageBroker.ReadMessagesAsync(this.Id)` 读取所有待处理消息
   - 过滤 `SubType == "user_forward"` 的消息
   - 追加到 `chatHistory` 作为新的 user turn（内容带 `[用户追加输入]` 前缀以区分原始任务）
   - 非用户转发消息（如 permission_response）不在此消费，保持原有路由
3. `SendMessageToAgentAsync` (`AgentServiceImpl.cs:346`) — `FromAgentId` 参数化：新增 `ForwardUserInputToAgentAsync(agentId, message, ct)`，设 `FromAgentId = "user"` + `SubType = "user_forward"`

**风险**：`ReadMessagesAsync` 返回 `IAsyncEnumerable`，`ReadAllAsync` 会阻塞等待新消息。需用 `TryRead` 非阻塞方式 drain 已有消息，不等待新消息。可能需要 `IAgentMessageBroker` 新增 `TryDrainMessagesAsync` 方法。

**验证**：单元测试 — 向子代理消息队列写入 user_forward 消息 → 子代理下一轮 ChatHistory 包含该消息。

---

### 阶段2：运行中子代理注册表

**目标**：维护"当前运行中子代理"列表，供主循环查询以决定输入路由。

**修改**：
1. `AgentServiceImpl` — 新增 `ConcurrentDictionary<string, RunningAgentEntry> _runningAgents`，记录 agentId、模式（前台/后台）、启动时间
2. `SpawnAgentAsync` (L96) — 启动时注册到 `_runningAgents`
3. `WaitForAgentAsync` / 子代理完成回调 — 从 `_runningAgents` 移除
4. `IAgentService` — 新增 `IReadOnlyCollection<RunningAgentEntry> GetRunningAgents()`
5. `RunningAgentEntry` [新] — record(agentId, IsForeground, StartedAt, DisplayName)

**验证**：单元测试 — Spawn → GetRunningAgents 包含 → WaitFor 完成 → GetRunningAgents 不包含。

---

### 阶段3：主循环并发改造 + 输入路由门控

**目标**：前台子代理运行时，主循环不阻塞，用户输入可被读取并路由。

**修改**：
1. `SubAgentInputGate.cs` [新] — 类似 `ConfirmationGate` 但支持多 agent 路由：
   ```csharp
   internal static class SubAgentInputGate
   {
       internal static volatile bool HasRunningSubAgent;
       internal static Channel<string>? PendingForwardInputs; // 用户待转发输入
   }
   ```
2. `ReplLoopStep.InvokeAsync` (L88-161) — 改造主循环：
   - 在 `await session.ProcessUserInputAsync(combined, stepCts.Token)` (L122) **之前**检查 `SubAgentInputGate.HasRunningSubAgent`
   - 若有运行中子代理 → 用户输入写入 `PendingForwardInputs` channel，`continue`（不进 ProcessUserInputAsync）
   - 若无 → 走原有 `ProcessUserInputAsync` 路径
   - **关键**：`ProcessUserInputAsync` 内部子代理前台运行时，主循环仍卡在 await。需要将前台子代理的输出流式回传，同时主循环能并发读输入。
   
   **并发模型**：将 `ProcessUserInputAsync` 的子代理前台执行改为"启动 + 流式输出 + 并发读输入"：
   - 子代理输出 → 实时显示给用户
   - 用户输入 → `SubAgentInputGate.PendingForwardInputs` → 转发决策 → 子代理消息队列
3. `ConfirmationGate.cs` — 保持不变（权限确认优先级高于子代理转发；若同时存在，权限确认先消费）

**风险**：这是最大的架构改动。`ProcessUserInputAsync` → `StreamResponseAsync` → `ChatService` → LLM 调用 Agent 工具 → `SpawnAgentAsync` 前台 await，整条链路阻塞。要改为并发，需要：
- 前台子代理也走流式 `RunAgentStreamAsync`（已存在，L68 of IAgentService）
- Agent 工具 Handler 前台模式改为返回流式输出而非阻塞 await
- 主循环在子代理流式输出期间并发读用户输入

**验证**：E2E — 启动前台子代理（长任务）→ 用户发送追加输入 → 验证子代理收到并处理。

---

### 阶段4：主代理 LLM 协同决策

**目标**：用户输入转发前，经主代理 LLM 判断是否转发、给哪个子代理、如何包装。

**修改**：
1. `UserInputForwardRouter.cs` [新] — 路由决策器：
   - 输入：用户原始输入 + 当前运行中子代理列表（含各自任务描述）
   - 调用主代理 LLM（轻量、专用 routing prompt）判断：
     - `shouldForward: bool`
     - `targetAgentId: string?`
     - `wrappedMessage: string`（包装后的消息，可附加上下文）
   - 输出：路由决策
2. `ReplLoopStep` — 从 `SubAgentInputGate.PendingForwardInputs` 读取用户输入 → `UserInputForwardRouter.DecideAsync` → 转发到目标子代理消息队列
3. 主代理对话历史记录：`[用户向子代理 {displayName} 追加输入: {摘要}]`，子代理完成后主代理 LLM 能感知交互过程
4. 若 LLM 决策 `shouldForward = false` → 输入排队等待子代理完成后作为主代理新输入处理

**Routing prompt 设计**：
```
你正在协助用户与多个子智能体协作。当前运行中的子智能体：
{agentId1} ({displayName1}): {任务描述1}
{agentId2} ({displayName2}): {任务描述2}

用户输入: "{userInput}"

判断：
1. 这条输入是否应转发给某个运行中的子智能体？（true/false）
2. 若是，目标子智能体 ID？
3. 包装后的消息内容（可附加必要上下文）？

输出 JSON: {"shouldForward": bool, "targetAgentId": string?, "wrappedMessage": string}
```

**验证**：单元测试 — mock LLM 返回决策 → 验证路由正确；E2E — 多子代理运行时用户输入路由到正确目标。

## 关键技术挑战与应对

| 挑战 | 应对 |
|------|------|
| `ReadMessagesAsync` 的 `ReadAllAsync` 阻塞等待 | 新增 `TryDrainMessagesAsync` 非阻塞 drain 已有消息 |
| 前台子代理阻塞主循环 | 前台模式改用 `RunAgentStreamAsync` 流式 + 并发读输入 |
| Agent 工具前台返回语义变更 | 工具返回流式输出，主代理 LLM 边消费边处理用户输入 |
| 多子代理输入路由 | 主代理 LLM 协同决策（阶段4） |
| 主代理 LLM 在子代理运行时被唤醒 | 独立轻量 LLM 调用（routing prompt），不干扰主对话流 |

## 不做的事

- 不改 `MailboxPoller`（跨进程 teammate 机制，与本设计无关）
- 不改后台模式 fire-and-forget 语义（后台子代理仍独立运行，只是额外可接收转发）
- 不改 `ConfirmationGate` 权限确认机制（保持优先级）
- 不引入跨进程通信（本设计是进程内转发）

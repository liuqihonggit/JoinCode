## 三、问题诊断

### 3.1 工具分散问题（最严重）

**McpTool 文件分布在 3 处，共 73 个文件**：

| 位置 | 文件数 | 内容 |
|------|--------|------|
| `core/execution/Hands/src/ToolHandlers/Handlers/` | 27 | 内置工具（File/Git/Search/Shell/Web/Agent/Desktop...） |
| `core/execution/McpToolDispatch/src/` | 10 | 代码工具（CodeAnalysis/CodeGen/CodeIndex/Graph/Lsp）+ 核心工具（AgentSummary/Cron/Goal/Sandbox） |
| `services/Mcp/src/` | 36 | MCP服务工具（GitHub/Skill/Task/Terminal/Communication/Dev...） |

**后果**：找一个 editor 工具需要在 3 处搜索，read/edit/bash 分散在 `DevTools/FileToolHandlers.cs`（read/write/edit/delete）和 `SystemTools/Shell/`（bash/powershell）。

### 3.2 提示词分散问题

| 位置 | 内容 |
|------|------|
| `foundation/Abstractions/01-ai/Prompts/ToolPrompts/` | 按功能分 Agent/File/Planning/Search/Shell |
| `core/execution/Brain/src/Prompts/Sections/` | 按 Agent/Domain 分（系统提示词组装） |

**后果**：同一工具（如 file_read）的 handler 在 `core/execution/Hands/`，prompt 在 `foundation/Abstractions/01-ai/Prompts/ToolPrompts/File/`，相隔多层。

### 3.3 "脑/眼/手"分类的不适点

| 领域 | 抽象层（Abstractions） | 实现层（core/services） | 问题 |
|------|------------------------|------------------------|------|
| 脑 | 02-brain | Brain + Dream | Dream 是"脑"还是"服务"？ |
| 手 | 03-hands | Hands | Hands 包含 File/Shell/Web/Agent 等异质工具 |
| 眼 | 06-perception | Eyes + Vision + CodeIndex | 三个实现对应一个抽象，职责不清 |
| 守卫 | 04-guard | Guard | 一致 |
| 记忆 | 05-memory | ? | 抽象有实现无独立项目 |
| 代理 | 07-agents | Agents | 一致 |

**核心问题**：工具本质是"功能"（read/edit/bash/github/agent...），"脑/眼/手"是隐喻而非功能分类，导致同一功能被拆到多个领域。

### 3.4 违反约定统计

|--------|------|------|
| `foundation/Abstractions/` 混排 | 10文件夹 + 3文件 | 纯文件夹 |
| `services/` 混排 | 7文件夹 + 1文件 | 纯文件夹 |
| `core/execution/Hands/src/` 混排 | 17文件夹 + 2文件 | 纯文件夹 |
| `core/execution/Brain/src/` 混排 | 9文件夹 + 2文件 | 纯文件夹 |
| `SystemTools/` 混排 | 3文件夹 + 7文件 | 纯文件夹 |

| `FileToolHandlers.cs` 过大 | 1972行 | 应拆分 |

## 四、改革方向（用户指定）

从 **"脑/眼/手"领域驱动** 改为 **"功能驱动"**：

```
root/
├── builtin/              # 内置工具（read/edit/bash等，原 Hands 中的工具）
│   ├── shared/           # 本层共享助手
│   ├── builtin_read/     # read 工具
│   │   └── private/      # read 私人助手
│   ├── builtin_edit/
│   │   └── private/
│   └── builtin_bash/
│       └── private/
├── mcp/                  # MCP 工具
│   ├── shared/
│   ├── mcp_read/
│   │   └── private/
│   └── ...
├── server/               # 各种服务（Bridge/Vision/CodeIndex...）
│   ├── shared/
│   ├── server_xx/
│   │   └── private/
│   └── ...
├── prompts/              # 提示词（与工具分离）
│   ├── shared/
│   ├── builtin/          # 内置工具的提示词
│   │   ├── shared/
│   │   ├── read/
│   │   └── edit/
│   ├── mcp/              # MCP 工具的提示词
│   └── server/           # 服务的提示词
├── slash/                # 斜杠命令
│   ├── shared/
│   └── slash_xx/
└── projects/             # 项目（app/slnx等）
```

## 五、关键决策点（需用户确认）

### 决策1：改革范围

- **方案A：仅改工具组织**（小改）— 只重组 `ToolHandlers` 和 `Prompts`，七层架构不变
- **方案B：改 core+services**（中改）— 重组 core/execution 和 services 为 builtin/mcp/server
- **方案C：全量迁移**（大改）— 七层架构全部重组为功能驱动，废弃"脑/眼/手"

### 决策2：七层架构是否保留

- **保留**：generators → foundation → infrastructure → core → services → composition → app 的编译依赖链不变，只改各层内部组织
- **废弃**：按 builtin/mcp/server/prompts 重新分层，编译依赖链重组

### 决策3：foundation/Abstractions 的"脑/眼/手"编号

- **保留编号**：00-core ~ 09-composition 不变，只改内部
- **改为功能前缀**：00-core → 00-shared, 01-ai → 01-llm, 02-brain → 02-planning, 03-hands → 03-tools...

### 决策4：csproj 粒度

- **现状**：Hands.csproj 包含所有内置工具（一个大项目）
- **方案A**：每个工具一个 csproj（极细粒度，编译慢但隔离好）
- **方案B**：按功能分组（builtin.csproj 包含 read/edit/bash，每个工具是子目录）

### 决策5：private/shared 的含义

- **private**：该工具专用的辅助类、扩展、内部服务
- **shared**：本层所有工具共享的辅助类、基类、接口

# 绝对超时纵深防御机制设计

> 日期: 2026-08-09
> 状态: 设计待确认

## 1. 目标

为 Hands 层工具执行（Shell/代码/搜索/Hook）建立三道防线：

```
Layer 1: 2分钟绝对倒计时 → Kill 进程, 返回超时错误
Layer 2: 超时错误触发 OnError 工具注入 → LLM 可调用 resume_timed_out_task 续期
Layer 3: 续期后每10分钟返回"仍在运行"状态 → LLM 决策 continue/stop
```

## 2. 现有基础设施（复用）

| 设施 | 位置 | 作用 |
|------|------|------|
| `ToolKind.OnError` | `McpToolAttribute.cs:52` | 标记工具为"仅错误时注入"，不出现在首次系统提示词 |
| `OnErrorToolInjectionMiddleware` | `McpToolDispatch/Core/Middleware/` | 工具失败时自动注入 OnError 工具说明 + 历史分析 |
| `ErrorRecoveryToolHandlers` | `Hands/ToolHandlers/Handlers/SystemTools/` | 现有 OnError 工具模式参考 |
| `ToolResult.InjectedMessages` | `ToolModels.cs:166` | 工具结果可注入消息到 LLM 对话 |
| `SandboxManager.ContinueExecutionAsync` | `Guard/Security/Sandbox/` | 现有"超时→LLM决策wait/stop→续等"模式参考 |
| `ShellPipelineContext.OverrideTimeout` | `Shell/` | 中间件可覆盖工具超时 |

**关键发现**: Layer 2 的"报错时才弹出工具,不注入首次提示词"已有完整基础设施 — `ToolKind.OnError` + `OnErrorToolInjectionMiddleware`。无需新建动态注入机制。

#### 3.0.3 超时策略类型

```csharp
/// <summary>工具超时策略</summary>
public sealed record ToolTimeoutPolicy
{
    /// <summary>绝对超时秒数, null=无限制</summary>
    public int? AbsoluteTimeoutSeconds { get; init; }

    /// <summary>是否支持续期（resume/continue/stop）</summary>
    public bool SupportsResume { get; init; }

    /// <summary>超时是否kill进程</summary>
    public bool KillOnTimeout { get; init; }

    /// <summary>无限制</summary>
    public static readonly ToolTimeoutPolicy None = new();

    /// <summary>2分钟绝对超时 + kill + 可续期</summary>
    public static readonly ToolTimeoutPolicy AbsoluteTwoMinutes = new()
    {
        AbsoluteTimeoutSeconds = 120,
        SupportsResume = true,
        KillOnTimeout = true,
    };
}
```

### 3.1 Layer 1: 2分钟绝对倒计时

#### 3.1.1 AbsoluteTimeoutMiddleware

**位置**: `core/execution/Hands/src/ToolHandlers/Handlers/SystemTools/Shell/AbsoluteTimeoutMiddleware.cs`

**职责**: 读取 `context.Handler.TimeoutPolicy`,按策略截断超时

```
管道顺序:
  ... → ShellValidationMiddleware → AbsoluteTimeoutMiddleware → ShellExecutionMiddleware → ...
```

**逻辑**:
1. 读取 `context.Handler?.TimeoutPolicy`（从类继承关系确定）
2. 如果 `policy.AbsoluteTimeoutSeconds is { } seconds`:
   - `effectiveTimeout = Math.Min(context.Timeout ?? int.MaxValue, seconds * 1000)`
   - 设置 `context.OverrideTimeout = effectiveTimeout`
3. 如果 `policy == ToolTimeoutPolicy.None` → 不干预（长期运行工具）

**优势**: 通过类继承关系,一眼看出哪些工具是2min、哪些是长期的。新增工具时继承正确的组即可,无需修改中间件或配置。

### 3.2 Layer 2: 超时续期工具（OnError 动态注入）

#### 3.2.1 新增 TimeoutRecoveryToolHandlers

**位置**: `core/execution/Hands/src/ToolHandlers/Handlers/SystemTools/TimeoutRecoveryToolHandlers.cs`

**标记**: `[McpToolDispatch(ToolCategory.ErrorRecovery, Kind = ToolKind.OnError)]`

**工具列表**:

| 工具名 | 参数 | GroupName | 说明 |
|--------|------|-----------|------|
| `resume_timed_out_task` | `original_command`, `original_tool`, `timeout_minutes=10` | "Bash", "PowerShell" | 恢复超时任务,默认10分钟续期 |
| `continue_long_running_task` | `task_id`, `additional_minutes=10` | "Bash", "PowerShell" | 继续等待运行中的任务 |
| `stop_long_running_task` | `task_id` | "Bash", "PowerShell" | 终止运行中的任务 |

**流程**:
```
LLM 调用 bash("dotnet build") → 2分钟超时 → 返回 IsError=true
    ↓
OnErrorToolInjectionMiddleware 检测到错误
    ↓
注入消息: "工具 'Bash' 执行失败... 以下修复工具可用: resume_timed_out_task..."
    ↓
LLM 看到建议,调用 resume_timed_out_task(original_command="dotnet build", original_tool="Bash")
    ↓
resume_timed_out_task 以10分钟超时重新执行命令
    ↓
10分钟内完成 → 返回结果
10分钟超时 → 返回"任务已运行10分钟,仍在继续. 调用 continue_long_running_task 继续等待"
    ↓
LLM 调用 continue_long_running_task(task_id, additional_minutes=10)
    ↓
（循环,形成10分钟周期提示）
```

### 3.3 Layer 3: 10分钟周期提示

**实现方式**: `resume_timed_out_task` 和 `continue_long_running_task` 的超时行为

**不是后台定时器注入**,而是:
1. 续期工具以 `timeout_minutes`（默认10）为超时启动命令
2. 超时后**不kill进程**,返回"仍在运行"状态（复用 SandboxManager 模式）
3. LLM 收到"任务已运行N分钟,仍在继续"的提示
4. LLM 决策: `continue_long_running_task`（续等）或 `stop_long_running_task`（终止）

**为什么不用后台定时器**:
- 工具执行是同步的,LLM 在等待工具返回
- 后台定时器注入消息需要中断 LLM 推理,架构复杂度高
- "超时返回+LLM决策"模式已被 SandboxManager 验证可行,且更简单

## 7. 与现有 SandboxManager 模式的对比

| 维度 | SandboxManager | 本设计 |
|------|----------------|--------|
| 超时行为 | 不kill,返回TimedOut | kill,返回IsError |
| LLM决策 | wait/stop | resume/continue/stop |
| 续等机制 | ContinueExecutionAsync | continue_long_running_task |
| 进程状态 | 保留在卫星进程 | 保留在LongRunningTaskRegistry |
| 适用场景 | Sandbox内执行 | 所有Shell工具执行 |
| 首次提示 | 工具始终可见 | 续期工具仅错误时可见 |

**为什么超时后kill而不是保留进程**:
- Shell工具直接在主机执行,不像Sandbox有卫星进程托管
- kill后通过 `resume_timed_out_task` 重新启动,更干净
- 避免僵尸进程积累

**为什么续期工具是kill+重启而不是续等原进程**:
- 原进程已被kill,无法续等
- 重启更安全: 清理所有资源(文件锁/内存)
- LLM可以看到之前的stdout/stderr,决定是否值得重试

## 8. 风险与缓解

| 风险 | 缓解 |
|------|------|
| 重启丢失进度 | resume结果包含之前的stdout/stderr摘要 |
| LLM无限循环续期 | LongRunningTaskRegistry 限制最大续期次数(默认5次) |
| 续期工具被滥用 | ToolKind.OnError 确保仅在错误时可用 |
| 2分钟太短 | 可配置 AbsoluteTimeoutSeconds,环境变量覆盖 |
| 进程kill不干净 | process.Kill(entireProcessTree: true) |

# 统一网络重试 24h 方案设计

> 状态：已实现 (Step 1-9 完成, commit 25fe51bad..205c9e0bb; DI 接入 commit 683141b41..a10fb9efe)
> 创建：2026-08-23
> 决策来源：用户要求"全部网络统一一个位置重试，不打爆服务器" + "24h 尝试，随机数，重试间隔不断增大"

## 1. 背景与问题

### 1.1 现状：多层嵌套重试导致请求放大

当前系统有 **6 类、15+ 处** 各自独立的重试逻辑。一个 LLM 请求的最坏重试路径：

```
BridgeMain 轮询
  └─ BridgeBackoffStrategy          [10分钟放弃]           ①
      └─ BridgeApiClient.SendWithRetryAsync  [N次]         ②
          └─ ApiClient.RetryPolicy  [3次]                 ③
              └─ ResilientHttpExecutor [3次,30s]          ④
                  └─ HttpClient.SendAsync
```

最坏情况：`① × ② × ③ × ④` 单请求被重试数十次，**打爆对端服务器**。

### 1.2 现状：最长重试仅 10 分钟

| 组件 | 放弃阈值 |
|------|----------|
| `ResilientHttpExecutor` | MaxRetries=3, ~90s |
| `BridgeBackoffStrategy` | **10 分钟**（最长） |
| `WaitForNetworkAsync` | 30s 超时 |

用户需要 **24h 持续尝试**，当前全部不支持。

### 1.3 用户诉求

1. **统一一个位置重试** — 消除嵌套放大，保护对端服务器
2. **24h 预算** — 网络长期失败时持续尝试 24h
3. **随机数（抖动）** — 防止多客户端同步重试（thundering herd）
4. **重试间隔不断增大** — 指数退避到上限后稳态

## 2. 设计目标

| 目标 | 衡量标准 |
|------|----------|
| 唯一重试点 | 所有出站 HTTP 请求-响应只在一处重试 |
| 24h 预算 | 总重试时间 ≤ 24h，到时抛 `NetworkRetryBudgetExhaustedException` |
| 指数退避 + 稳态 | 2s→4s→...→5min 上限，之后每 ~5min 一次 |
| 抖动 | ±25% 随机抖动，防同步 |
| 网络感知 | 网络不可用时等待恢复（不消耗重试次数），恢复后继续 |
| 长连接参数统一 | SSE/SSH/Bridge 重连退避参数从统一配置取 |
| 不打爆服务器 | 嵌套层全部降级为透传（MaxRetries=0） |

## 3. 24h 重试算法

### 3.1 退避公式

```
delay(n) = min(BaseDelay × 2^n, MaxDelay) × jitter
jitter   = 1 + Random.Shared.NextDouble() × 0.5 - 0.25   // [0.75, 1.25]
```

参数：
- `BaseDelay = 2s`
- `MaxDelay = 5min = 300s`
- `TotalBudget = 24h = 86400s`

### 3.2 时序推演

| 次数 n | 基础延迟 | 实际延迟（含抖动范围） | 累计耗时 |
|--------|----------|----------------------|----------|
| 0 | 2s | 1.5s ~ 2.5s | ~2s |
| 1 | 4s | 3s ~ 5s | ~6s |
| 2 | 8s | 6s ~ 10s | ~14s |
| 3 | 16s | 12s ~ 20s | ~30s |
| 4 | 32s | 24s ~ 40s | ~62s |
| 5 | 64s | 48s ~ 80s | ~126s |
| 6 | 128s | 96s ~ 160s | ~254s |
| 7 | 256s | 192s ~ 320s | ~510s |
| 8 | 300s（上限） | 225s ~ 375s | ~810s |
| 9+ | 300s（稳态） | 225s ~ 375s | 每次 ~5min |

- **指数阶段**：n=0~7，总耗时 ~510s（~8.5min）
- **稳态阶段**：n=8+，每次 ~5min
- **24h 内总重试次数**：~9（指数） + (86400-810)/300 ≈ **294 次**
- **24h 预算到时**：抛 `NetworkRetryBudgetExhaustedException`

### 3.3 网络不可用处理

```
网络不可用时：
  - 暂停重试计时（不消耗 TotalBudget）
  - 无限等待 INetworkConnectivityService.StateChanged 事件
  - 网络恢复后继续重试，预算计时恢复
```

> 决策：24h 预算 = "有网络时的重试总时长"。网络不可用期间不计时，避免"网络断 23h + 恢复后只重试 1h 就放弃"的不合理场景。
>
> 替代方案（已否决）：24h 含等待网络时间 — 网络长期断会导致预算耗尽放弃，不符合"24h 尝试"语义。

## 4. 统一重试 Gateway 设计

### 4.1 方案选型：升级 ResilientHttpExecutor

**选定**：在现有 `ResilientHttpExecutor`（`infrastructure/Infrastructure/Http/ResilientHttpExecutor.cs`）上扩展。

**理由**：
- 已在 Infrastructure 层（HTTP 出口层），位置正确
- 已支持 `INetworkConnectivityService` 注入与 `WaitForNetworkAsync`
- 已有 `CalculateDelay` 指数退避 + 抖动逻辑，只需扩展
- 已在 LLM 层注入（`ServiceRegistration.CreateLlmResilientExecutor`）

**否决方案**：新建 `UnifiedNetworkRetryGateway` 类 — 新增一层，ResilientHttpExecutor 降级为内部实现，增加复杂度无收益。

### 4.3 ResilientHttpExecutor 核心循环改造

```csharp
// 伪代码 — ExecuteAsync 改为预算驱动
public async Task<HttpResponseMessage> ExecuteAsync(...)
{
    var budget = _policy.Retry?.TotalBudget;
    var sw = Stopwatch.StartNew();
    var attempt = 0;
    var budgetPausedTime = TimeSpan.Zero;
    var networkUnavailableStart = (DateTime?)null;

    while (true)
    {
        // 预算检查
        var elapsed = sw.Elapsed - budgetPausedTime;
        if (budget.HasValue && elapsed >= budget.Value)
            throw new NetworkRetryBudgetExhaustedException(
                $"[{_policy.Name}] 24h 重试预算耗尽 (尝试 {attempt} 次, 实际 {elapsed})");

        try
        {
            var response = await ExecuteOnceAsync(operation, operationName, effectiveCt);
            _circuitBreaker?.RecordSuccess();
            return response;
        }
        catch (OperationCanceledException ex) when (IsUserCancellation(ex, ct)) { throw; }
        catch (Exception ex) when (ShouldRetry(ex, retry))
        {
            attempt++;
            var delay = CalculateDelay(attempt, retry);  // 2s→5min 稳态 + ±25% 抖动

            // 网络不可用：暂停预算 + 无限等待恢复
            if (_networkService is not null && !_networkService.IsNetworkAvailable())
            {
                networkUnavailableStart ??= _clock.GetUtcNow();
                await WaitForNetworkRecoveryAsync(ct);  // 无限等待 StateChanged，不占预算
                if (networkUnavailableStart.HasValue)
                    budgetPausedTime += _clock.GetUtcNow() - networkUnavailableStart.Value;
                networkUnavailableStart = null;
            }

            await Task.Delay(delay, ct);
        }
        catch (Exception ex)
        {
            _circuitBreaker?.RecordFailure();
            throw;
        }
    }
}
```

### 4.4 WaitForNetworkAsync 改造

```csharp
// 当前：30s 超时
// 改为：无限等待网络恢复（受外层 TotalBudget 约束）
private async Task WaitForNetworkRecoveryAsync(CancellationToken ct)
{
    if (_networkService is null || _networkService.IsNetworkAvailable()) return;

    var tcs = new TaskCompletionSource<bool>(TaskCreationOptions.RunContinuationsAsynchronously);
    EventHandler<NetworkConnectivityChangedEventArgs> handler = (_, e) =>
    {
        if (e.CurrentState != NetworkConnectivityState.Offline) tcs.TrySetResult(true);
    };
    _networkService.StateChanged += handler;
    try { await tcs.Task.WaitAsync(TimeSpan.MaxValue, ct); }  // 无限等待，由 ct 取消
    finally { _networkService.StateChanged -= handler; }
}
```

## 7. 时序图

### 7.1 正常重试（网络可用）

```
调用方 ──→ Gateway.ExecuteAsync
              │ attempt=0, delay=2s   失败
              │ sleep 2s
              │ attempt=1, delay=4s   失败
              │ sleep 4s
              │ ...
              │ attempt=8, delay=300s 失败
              │ sleep 300s
              │ attempt=9, delay=300s 成功 ← 返回
调用方 ←─── 响应
```

### 7.2 网络中断恢复

```
调用方 ──→ Gateway.ExecuteAsync
              │ attempt=0 失败 (HttpRequestException)
              │ 检测网络不可用 → 暂停预算计时
              │ 等待 StateChanged 事件...（不消耗 24h 预算）
              │                          网络恢复事件到达
              │ 恢复预算计时
              │ delay=2s, attempt=1 重试 成功 ← 返回
调用方 ←─── 响应
```

### 7.3 24h 预算耗尽

```
调用方 ──→ Gateway.ExecuteAsync
              │ ... 294 次重试 ...
              │ elapsed = 24h ≥ TotalBudget
              │ throw NetworkRetryBudgetExhaustedException
调用方 ←─── 异常（由上层决定重启/告警/退出）
```

## 8. 接入点与降级策略

### 8.1 请求-响应型降级模式

```csharp
// ApiClient 改造示例
// 改前：
return await _retryPolicy.ExecuteAsync(...);  // 自己重试 3 次

// 改后：
return await operation(ct);  // 单次执行，重试交给外层 Gateway
```

**关键**：`ApiClient` 的调用方需确保用 `ResilientHttpExecutor.ExecuteAsync` 包裹。若 `ApiClient` 直接被调用无 Gateway 包裹，则该路径无重试（可接受：非 LLM 的 API 调用通常不需 24h 重试）。

### 8.2 长连接重连参数统一模式

```csharp
// SseAgentTransport 改造示例
```

## 10. 风险与回滚

| 风险 | 缓解 |
|------|------|
| ApiClient 降级后某些路径无 Gateway 包裹 → 无重试 | 改动前梳理所有 ApiClient 调用方，确认有 Gateway 包裹；无包裹的路径保留原轻量重试 |
| BridgeBackoffStrategy 24h 不放弃 → Bridge 永久卡住 | 保留 `onFatalExit` 回调，24h 到时触发 |
| 预算计时精度（Stopwatch 漂移） | 可接受，24h 级别 ±1s 误差无影响 |
| 网络抖动导致频繁暂停/恢复预算 | `StateChanged` 已有去重（状态不变不触发） |

**回滚**：`RetryConfig.TotalBudget = null` 时回退到 `MaxRetries` 驱动（向后兼容）。

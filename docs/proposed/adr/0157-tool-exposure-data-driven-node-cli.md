# ADR 0157: 去生成器 + 基础工具 YAML 注册 + 全量工具独立 CLI.exe + CLI 搜索下钻

- 状态：proposed（v3 修订 — 按用户 2026-11-15 后续指令改为「按分组一个 exe + 特性原封不动 + 复用现有说明做 -h」；v1 作废，v2 的「540 个独立 exe / 描述搬到新 YAML」已被本版取代）
- 日期：2026-11-15
- 关联：ADR 0149（减少 exe 数量 — **本次显式收窄适用范围**）、ADR 0137（功能域就近隔离）、DSG048（节点插件继承架构）、DSG018（工具渐进式暴露 — **本次判定为错误层**）
- 上游用户指令（2026-11-15 原文）：
  1. 我想扔掉工具的源码生成器
  2. 我认为可以通过 yml 来注册基础工具
  3. 除了基础之外的全部转为独立的 CLI.exe 工具，这样可以各自被 `-h` 帮助说明让 LLM 自行按需阅读
  4. 分班再分组，是 AI 供应商协议本身不提供，所以 mcp 使用这个做法是错误的，但是 CLI 层面则可以通过搜索功能下钻探索，此时才是正确的

## 1. 核心洞察（第 4 点）

**MCP / AI 供应商协议只提供扁平的 `tools` 数组，不提供分组、分级、下钻。** 项目现有的 `tool_groups` 自定义字段、提示词里教 LLM 的 `list_groups` → `map[组]` → `map[组][工具]` 三级下钻，都是在**错误的层**模拟一个协议不存在的能力。症状即证据：

| 症状 | 原始证据 |
|------|---------|
| 真实 API 直接忽略分组字段 | `modules/llm/docs/task/TASK010-ResponsesAPI支持任务.md:108`：「`tool_groups` + `tool_description_request` 是自定义协议，真实 DeepSeek API 忽略这两个字段」 |
| 占位符/延迟加载只在单一供应商实现 | `FilterDeferredTools` 仅见于 `AnthropicQueryService.cs:138` |
| 下钻能力要靠提示词"教"出来 | `ToolsSection.cs:33-40` 用 8 行系统提示词解释三级语法 |
| 补回的 schema 永久滞留上下文 | `ToolsSection.cs:36` 要求 LLM 直取 schema 后调用 |

**CLI / 文件系统原生拥有路径树与搜索**：`ls`、`find`、`grep`、`<tool> -h` 是协议无关的，LLM 用已有的 bash 工具即可按需探索，探索结果查完即弃、不占常驻上下文。因此在 CLI 层做下钻是正确的，在 MCP 层做分组是错误的。这与 harness2「差异编码为数据 + 靠目录树构造性复用」、DSH「Service/Context 不靠特性标注」同源。

## 3. 决策

### 3.1 四层分离

| 层 | 内容 | 对 LLM 可见性 |
|----|------|--------------|
| **基础工具层**（4 个） | 读 / 写 / 编译 / bash，由 `resources/tools/base.yaml` 声明注册 | 以完整 schema 进入协议原生 `tools` 字段 |
| **CLI 工具层**（其余全部） | 每个工具一个独立 exe + `node.yaml` 自描述 + `-h` | 完全不进提示词，LLM 用 bash 按需 `ls` / 搜索 / `-h` |
| **发现层** | 目录树 + 关键词搜索下钻，**CLI 层实现，不进 MCP** | 按需查询，查完即弃 |
| **描述数据层** | 参数描述从 C# 特性迁到 YAML（单一数据源） | 永不注入 |

### 3.2 逐条落地

| 用户指令 | 决策 |
|---------|------|
| ① 扔掉工具源码生成器 | **v3 修订**：`[McpTool]` / `[McpToolParameter]` 特性**全部保留不动** — 它们是现成的描述单一数据源。生成器退役推迟到所有消费方切换完毕之后，避免在迁移期制造两套说明。当前先用编译期只读扫描器复用特性文本 |
| ② yml 注册基础工具 | 保留 v2 决策：`resources/tools/base.yaml` 声明 4 个基础工具（读/写/编译/bash），由 `BaseToolRegistry` 内嵌资源加载 |
| ③ 其余全部转独立 CLI.exe | **v3 修订**：不是「每个工具一个 exe」，而是**按 `ToolCategory` 分组，每组一个独立 exe**（全仓实测 51 个分组，覆盖 546 个工具）。组内每个工具是 exe 的一个子命令；`-h` 分组总览 + `<工具名> -h` 单工具详情 |
| ④ CLI 搜索下钻 | 保留 v2 决策：`jcc tool find` / `tree` / `help` 基于目录树与分组索引；分组索引由脚本从现有特性生成，不放进 MCP、不进提示词 |

### 3.2.1 v3 的关键简化（用户 2026-11-15 指令）

> 「大部分的 mcp 特性是不需要改的，你只需要按照每个分组单独一个 cli.exe，这样就可以 bash 调用它们了。而且复用现有的 mcp 说明，来制造 -h 说明也很好。」

由此取消 v2 的「把参数描述从 C# 特性搬到新 `node.yaml`」这一整套数据迁移工作。新增 `scripts/migrate_mcp_tools_to_cli_nodes.py`：**只读**扫描 5248 个 .cs，按分组把现有特性说明渲染成 `help.txt`（编译期内嵌）+ 分组级 `node.yaml`（供下钻索引），不修改任何源 .cs、不重复写一份描述。

实测产出（**v3 归并后**）：扫描 5298 个 .cs / 发现 546 个工具 / 归入 **12 个功能大类** / 生成 46 个文件。初次直接用 `[McpTool]` 第三参数当组名曾炸出 51 个碎组（20 个组仅 1~3 个工具），经用户指出「分组应该不多」后，改为 `resources/tools/group_map.yaml` 单一映射表向上归并；42 个旧碎组目录按规则移到项目根 `.xxx/` 归档，未删除。

12 个大类与工具数：`github` 172、`system` 71、`media` 60、`agent` 59、`search` 47、`code` 32、`shell` 27、`mcp` 25、`tools` 18、`file` 13、`git` 10、`web` 5。`github` 单独成组避免单 exe 塞入过多工具；`worktree` 归 `agent` 使 `git` 组保持既有 10 个本地实现工具。新增分类只需在 YAML 登记，不在脚本加分支。

首个完整样板：`modules/tools/cli_nodes/groups/git/` → `jcc-tool-git.exe`，10 个 git 工具全部可用 BCL `Process` 实现，零引擎依赖；`-h` 文本完全来自现有特性。

### 3.2.2 12 个大类 exe（转发实现，git 组为本地实现样板）

`--emit-exe` 为每组生成 `jcc_tool_<组>.csproj` + `Program.cs`，统一 Import `cli_node.props`。生成物带 `GENERATED BY` 标记，脚本幂等覆盖；检测到手工实现（git 组）则跳过，绝不覆盖。

| 能力 | 实现 |
|------|------|
| `-h` / `<工具名> -h` | 内嵌 `help.txt`（现有特性渲染），零引擎依赖 |
| 工具执行 | 转发宿主 `jcc mcp_call <工具名> <argsJson>`，用 `ArgumentList` 传参不手工拼转义 |
| JSON 构造 | `JsonSerializerContext` 源生成（避免 AOT 的 IL3050），不手写字符串拼接 |
| 宿主缺失 | 退出码 3 + 四要素错误引导（原因/触发/拦截层/修复方式） |

**诚实边界**：exe 的控制流是独立的（自带 `-h`、可 bash 调用、零引擎引用），但执行能力按组分布——`git`/`file`/`code`/`search`/`shell`/`web`/`system`/`tools` 共 52 个工具已本地实现，其余由 exe 转发宿主。哪些工具真进程隔离由 `--list-local` 自报（见 3.2.8）。

### 3.2.3 混合模式（逐组做实的可持续路径）

用户 2026-11-15 选择「逐组做实本地实现」。设计要点：**不要求一次性实现 546 个工具**，每组独立推进且 exe 始终可用。

| 机制 | 说明 |
|------|------|
| 手工实现保护 | `Program.cs` 带 `// HANDCRAFTED` 标记，扫描器 `is_generated_or_missing` 优先识别并跳过覆盖；生成物带 `GENERATED BY` 可幂等重生成。12 组重跑实测：10 个生成物重生成、file/git 两个手工实现完整保留 |
| 本地优先 | `GroupCommands.Find(toolId)` 命中即本地执行（BCL），不启动宿主、零网络 |
| 转发兜底 | 未本地化的工具自动转发 `jcc mcp_call`，缺宿主时给四要素错误引导（退出码 3） |
| 描述不变 | `-h` 仍读内嵌 `help.txt`（现有特性渲染），手工实现不重复写任何说明 |

**第 2 个样板 `file` 组**：13 个工具中 11 个用 BCL 本地实现（`file_read/write/delete/edit/edit_regex/insert_lines/delete_lines/batch_edit`、`directory_list`、`file_snip_lines`、`file_snip_preview`）；`file_apply_patch`（unified diff）与 `send_user_file`（UI/链接）无零依赖实现，走转发兜底。每个命令是有名函数，必填参数缺失给 Rust 风格四要素引导。

真机验收（仅编译 `file` 组这一个改动项目，3.25s、0 警告）：`file_write` → `file_read` → `file_snip_preview` → `file_edit` 全链路本地跑通（仅在 artifacts 造临时探针文件，不触碰项目文件、未调用删除工具）；缺 `--file_path` 返回退出码 2 + 正确写法；`file_apply_patch` 返回退出码 3 + 宿主设置引导。

**已知限制**：
1. 工具 id 由脚本从 `XxxEnumConstants.Yyy` 末段转 snake_case 得出，可能与实际 MCP 注册名有偏差；转发前需按分组核对（脚本在 `help.txt` 保留原说明，未保留常量全名，后续补 `source` 字段）
2. 位置参数被转成 `arg1`/`arg2` 键，对以位置参数为主的工具（如 rg）转发可能不匹配；这类组优先改本地实现
3. 宿主需 `JCC_HOST_EXE` 或 jcc 在 PATH；无 Hub 环境另需 `JCC_ALLOW_DIRECT_FALLBACK=1`
4. **12 个分组 exe 已全部编译通过**（每个 2~4 秒、0 警告、apphost 各 160KB），只编译这 12 个新项目，**未跑全仓编译**；其中 `system` 组曾因组名生成 `JoinCode.CliNode.System` 命名空间导致 `System.ComponentModel` 解析失败，已用 `global::` 在模板层修复
5. 生成文件头部带 `GENERATED BY`，重跑扫描器会覆盖；手工改动请删除该标记或另建实现文件

**真机验收**：`jcc-tool-file.exe -h`（13 工具总览）、`file_delete -h`（只输出该工具参数）、未设宿主时错误引导（退出码 3）、设宿主后转发返回结构化 `TOOL_ERROR`（退出码 1，全程无副作用）。

### 3.2.4 进程隔离执行器 — `jcc tool call`（用户 2026-11-15 最终指令）

用户在逐组做实之后进一步明确目标：**「拆分成多个 exe（例如 mcp / 斜杠命令），拆分后 jcc 通过启动外部程序方式调用，也就是进程隔离」**，并要求 **jcc 真机启动验证**。这是把工具拆成 exe 的目的是所在——工具逻辑跑在独立进程，与宿主进程隔离。

**关键设计**：这条执行路径位于最外层子命令路由（ Program.cs 步骤 3 之前），**完全不初始化引擎 DI、不加载任何工具实现、不连 Hub**。jcc 在此仅是一个"启动器"：定位 exe → `Process.Start` → 透传参数 → 回传 stdout/stderr/退出码。工具实现运行在被启动的独立进程里。

| 能力 | 实现 |
|------|------|
| 命令形态 | `jcc tool call <分组> <工具名> [--参数 值 ...] [--exe <path>]` |
| exe 定位优先级 | `--exe` > `JCC_TOOL_EXE_DIR`（平铺）> `JCC_CLI_TOOLS_DIR/<组>` > `<jcc目录>/tools/<组>` > 仓库 `artifacts/bin/jcc_tool_<组>/{Debug,Release}/<tfm>/` |
| 参数透传 | `ProcessStartInfo.ArgumentList` 逐参数传递，不手工拼命令行字符串（空格/引号/特殊字符安全） |
| 结果回传 | stdout→stdout、stderr→stderr、子进程退出码→jcc 退出码 |
| 缺参/无组/启动失败 | 四要素错误引导，退出码 2 / 3 / 4 |

**真机验收 jcc 启动外部 exe（七连验，读取增量编译后的 jcc.exe）**：
1. `jcc tool call`（缺参）→ 退出码 2 + 正确写法引导 ✅
2. `jcc tool call file file_read --file_path …` → 返回文件内容，退出码 0 ✅（jcc 启动 file 组 exe，本地 BCL 实现）
3. `jcc tool call git git_status` → 返回真实 git 状态，退出码 0 ✅（jcc 启动 git 组 exe）
4. 参数含空格（`"probe with space.txt"`）→ 正确读取，退出码 0 ✅（ArgumentList 转义正确）
5. `--exe` 显式指定 git exe → 执行到工具参数校验，退出码 2 ✅（显式定位生效）
6. 不存在的组 → 四要素引导 + 查找顺序，退出码 3 ✅
7. 转发兜底组（code）无宿主时 → exe 的宿主引导透传，退出码 3 ✅（子进程退出码正确回传）

### 3.2.5 斜杠命令独立 exe — `jcc-slash`（用户「例如 mcp 和斜杠命令」的另一半）

用户原话是「拆分成多个 exe，**例如 mcp 和斜杠命令**」。mcp 侧已按 12 组落地，斜杠命令同样拆成独立 exe，避免只做一半。

| 项 | 实现 |
|----|------|
| exe | `jcc-tool-slash.exe`（99 个命令 / 15 个分类 / 14 个隐藏命令） |
| `-h` | 按分类分组列出全部命令 + 单命令参数段；文本来自现有 `[ChatCommand]` / `[ChatCommandArg]` 特性，零手写说明 |
| 生成 | `scripts/generate_slash_cli_node.py` 只读扫描（枚举 `[EnumValue]` 还原 `rate-limit-options` 这类真实名），生成 `help.txt` + `csproj`；`Program.cs` 手写（`HANDCRAFTED`），脚本不覆盖、不修改任何源 .cs |
| 执行 | 斜杠命令依赖会话状态（聊天上下文 / 服务容器），无法零依赖实现，统一转发宿主 `jcc slash_call`；jcc 侧用 `jcc tool call slash <命令>` 启动它，形成 `jcc → exe → jcc` 进程隔离链 |
| Git Bash 兼容 | 命令名归一化：`/agents` 被 MSYS 展开成 Windows 路径时取末段还原；`--exe` 等透传参数不受影响 |

真机验收：`jcc tool call slash -h`（99 命令总览，退出码 0）、`jcc tool call slash agents -h`（单命令参数，退出码 0）、`jcc tool call slash /agents -h`（经 Git Bash 展开后仍正确恢复，退出码 0）、`file` / `git` 组回归通过。

**诚实边界**：jcc 进程隔离执行已打通，但被启动的 exe 分两类——`git`/`file`/`shell`/`tools` 组是本地实现（真隔离，离开宿主可跑）；`slash` 组与其余 8 个分组仍是转发实现，exe 会再转发宿主（`jcc → exe → jcc` 进程链，工具逻辑仍落在宿主进程）。要做成完全隔离，需把这些组也逐组做实本地实现。

### 3.2.6 主请求链路切换 — 首轮 `tools` 从 506 降到 4（步骤 9）

前面把工具拆成 exe，只是把能力物理外置；**真正决定首提示词体积的开关在这里**：只要 `tools` 字段还是全量 schema，拆多少 exe 都不影响请求大小。

| 项 | 改动 |
|----|------|
| 数据源 | 三个 provider（OpenAI / Responses / Anthropic）的 `BuildToolsFromKernel` 全部删除，改为 `BuildBaseTools`：只保留 `resources/tools/base.yaml` 里登记的 id，其余 540+ 工具不再进入协议原生 `tools` 字段 |
| `tool_groups` | 退役——`request.ToolGroups` 不再写入（三个 Type 上的字段保留仅作兼容，恒为空） |
| 两阶段加载 | `CreateSecond*RequestWithDescriptions` 已无调用方，随 `tool_groups` 一起失效 |
| 提示词 | `ToolsSection` 重写：只推荐 `base.yaml` 里真实声明的工具，并给出 `jcc tool tree / find / help / call` 四步发现通道；删除 `Glob` / `Grep` / `TodoWrite`（已不在首轮清单）与 `tool_search` `list_groups` `map[...]` 三级下钻文案 |
| schema 来源 | 参数 schema 取内核元数据、描述取 `base.yaml`。理由：handler 就在内核里，用它的参数定义能保证 LLM 看到的必填项与执行期校验完全一致；而给模型看的文案仍以 YAML 为单一数据源 |
| 回归守卫 | `BuildBaseTools_*`（9 个单测，三个 provider 各 3 个）锁定「非基础工具一律不进 tools 字段、描述来自 YAML」 |

**同时修正了一个假工具**：`base.yaml` 原先登记的第 3 项 `code_execution` 在 546 个内核工具里**并不存在**（是凭空命名的）。步骤 9 一旦接上，LLM 会拿到一个永远「工具不存在」的槽位。编译/构建本就由 `bash` 覆盖，故改为真实高频的 `file_edit`（局部查找替换，与 `file_write` 的整体覆写互补）。`BaseToolRegistryTests` 7/7 通过，`jcc tool base` 真机输出已变为 `file_read / file_write / file_edit / bash`，`file_edit` 走进程隔离实跑成功（写→改→读回验证）。

### 3.2.7 自包含装配目录 — jcc 离开仓库开发布局也能启动子进程

进程隔离执行器有一处隐含前提：分组 exe 得能被找到。开发态靠仓库里的 `artifacts/bin/jcc_tool_<组>/`，发布态没有这个路径，等于「拆了 exe 但部署后调不到」。

| 项 | 实现 |
|----|------|
| 脚本 | `non_deliverables_tools/scripts/Pack-ToolNodes.ps1` → `<Target>/tools/<组>/`，每组装 apphost + 程序集 + `deps.json`/`runtimeconfig.json` + `node.yaml` + `help.txt` |
| 按需编译 | 只在缺 exe 时编该组；`obj` 被清过时先按需 restore 一次；单组失败不影响其余组，末尾汇总并返回非 0 |
| jcc 消费 | 目录发现与 exe 定位都认 `JCC_CLI_TOOLS_DIR`（`jcc tool tree` 首行会打印实际解析到的目录），或直接放到 `<jcc>/tools/` |
| 实测 | 13 组 / 9045 KB / 装配 23.6 秒；`jcc tool tree` 首行指向装配目录，`jcc tool call file file_read` 退出码 0，装配后的 exe 自带 `-h` |

**诚实边界**：装配产物是框架依赖构建（每组约 680 KB，含契约层 DLL），不是单文件；AOT 单文件本机不可测（缺 `advapi32.lib`，`reg.exe` 被安全策略拦截）。

### 3.2.8 入口统一与逐组做实进展（2026-11-16）

**入口统一**：13 个 exe 原本各写一份「`-h` / `--list-local` / 参数解析 / 本地分发 / 转发宿主 / 退出码」，到第 6 组时已经长出差异（catch 过滤器不同、未知工具提示各写一套）。现收到契约层 `CliNodeRunner` + `CliNodeDefinition`：

| 关注点 | 收口位置 |
|--------|----------|
| `-h` / `<工具> -h` / `--list-local` | `CliNodeRunner`（帮助文本仍读各组内嵌 `help.txt`，不重复维护说明） |
| 参数解析 | 一处实现，支持 `--k v`、`--k=v`、单横线短选项（`-i` / `-A 3`，排除 `-5` 这类负数） |
| 未知工具 | 按帮助文本的工具清单判定，给近似名建议（包含关系 + 编辑距离 ≤ 2），退出码 2 |
| 本地/转发分发 | `CliNodeDefinition.Resolve` 返回 null 即转发；本地异常统一映射退出码 2 并给下一步 |
| 转发宿主 | `jcc mcp_call <工具> <json>`，`ArgumentList` 传参，失败退出码 3 |

结果：13 组 `Program.cs` 退化为 10~20 行声明（git 组保留「工具 id → git 命令行」翻译，经 `ArgBag(options)` 复用已解析参数，不再有第二套 `--key` 规则）。

**逐组做实清单（`--list-local` 自报，共 52/546）**：

| 组 | 本地/总数 | 本地化依据 | 仍转发的部分及原因 |
|----|-----------|------------|--------------------|
| git | 10/10 | 参数→`git` 命令行 | — |
| file | 11/13 | BCL 文件读写 | `file_apply_patch`（补丁事务/冲突校验）、`send_user_file`（附件管道） |
| code | 10/32 | `.ipynb` 是纯 JSON，`JsonNode` 直读 | `lsp_*`（语言服务器进程）、`generate_*`/`analyze_*`（模型）、`recall_*`（宿主召回库） |
| search | 8/47 | glob 匹配器；grep 族优先 `rg --json`，缺失时内置扫描 | `code_index_*`（持久化 AST 索引）、`graph_*`（调用图存储）、semantic/document（向量模型） |
| shell | 6/27 | BCL 进程执行 | 构建/沙箱/终端会话（宿主进程树与中间件栈） |
| web | 2/5 | `HttpClient`（分块并发+续传）/ 自研 HTML→Markdown | `web_fetch`（二级 LLM 提炼）、`web_search`（供应商搜索）、`web_browser`（浏览器会话） |
| system | 3/71 | 纯等待 + 本进程信息 | `config_*`/`permission_*`/`agent_*`/`memory_*`/`analytics_*`（宿主存储与服务） |
| tools | 2/18 | BCL | `skill_*`/`tool_*`（宿主技能注册表与工具索引） |
| agent / mcp / media / github / slash | 0 | — | 计划/任务/团队共享状态、MCP 客户端连接、桌面控制与安全策略、`gh` 令牌与 API、斜杠命令派发 |

**判定原则（重要）**：只有「宿主无状态依赖」才本地实现。像 `memory_*`、`permission_*`、任务/计划类工具，其数据落在宿主持有的存储里——在 exe 内重写一份会分叉出第二个真相源（LLM 在 A 处写、宿主在 B 处读），比不隔离更糟。这类工具继续转发，并在 `node.yaml` 里标 `mode: host`，同时 `-h` 会打印「执行方式: host（转发宿主）」让调用方可审计。

**安全边界**：本地化的 `bash` / `powershell` 直连操作系统，绕过宿主 Shell 中间件栈与 `DangerousCommandCatalog`。生产环境命令执行仍应走宿主；该组本地实现只用于进程隔离验证与离线可用性，已在组入口注释中标注。

### 3.3 对 ADR 0149 的显式收窄

ADR 0149:18「减少 exe 数量 — 不要搞那么多 exe」在**交互宿主**语境下仍然成立（`jcc.exe` + `NativeGui.Host.exe` 保持），但**不适用于工具层**：工具 exe 不是用户交互宿主，而是能力的物理封装单元。本次决策把工具层从「宿主内进程」改为「独立可执行文件」，exe 数量显著增加。记录为对 0149 适用范围的收窄，而非整体废弃。

### 3.4 不做什么

- **不删除文件** — 生成器项目归档到 `.xxx/`，引用同步修复
- **不动 `[Register]` DI 生成器** — 838 处属服务注册，与工具 schema 是两回事
- **不新增 MCP 分组能力** — `tool_groups` 相关路径随工具迁移一并退役

### 4.1 依赖墙收敛实测（2026-11-15）

建立 `modules/tools/cli_nodes/cli_node.props` 共享配置：工具 exe 只引用 `Abstractions.Primitives.Tools` 契约层，关闭全仓分析器 / 代码风格 / 文档生成 / Structura 全局引用，AOT 改为发布阶段显式开关。最小样板为 `modules/tools/cli_nodes/sample/`。

| 指标 | 基线（`jcc-rg` 引 `Infrastructure`） | 收敛后（clean publish） | 变化 |
|------|-----------------------------------|------------------------|------|
| 依赖 DLL 数 | 81 | **5** | −94% |
| 输出目录体积 | 16 MB | **653 KB** | −96% |
| 构建依赖项目数 | 80+ | **2**（契约层 + 工具） | −97% |
| 首次编译 | 1m33s | 9.8s | −89% |
| 增量编译 | — | **1.94s** | 540 个串行约 17 分钟 |
| AOT 发布 | — | 本环境不可测（见下） | 环境限制 |

根因：`Infrastructure.csproj:17-95` 单项目挂 20+ ProjectReference + 5 个 Microsoft.Extensions 包 + 2 个源码生成器；`Directory.Build.props:148-152` 另给所有 net10.0 项目全局注入 `Structura`；`Directory.Build.props:64` 在 Release 全局开 AOT。三者叠加导致每个工具 exe 都被拖入整个引擎。

**AOT 实测的环境限制（如实记录）**：`dotnet publish -p:PublishAot=true` 在本机链接阶段报 `LNK1181: 无法打开输入文件 advapi32.lib`（Windows SDK 链接库不全），且工具链调用的 `reg.exe` 被安全策略拦截。按规则未重试、未绕过；AOT 单文件体积待具备完整 Windows SDK 的 CI 环境补测。当前 AOT 开关设计为 `-p:CliNodePublishAot=true` 显式启用，不影响日常编译速度。

**由此产生的批量迁移硬约束**：所有工具 exe 必须 Import `cli_node.props`，禁止新增 `Infrastructure` / 引擎 / DI 容器 / 源码生成器引用；`YamlDotNet.dll`（293 KB）是剩余依赖中的最大项，若后续需再压缩，方向是编译期把 `node.yaml` 转为内嵌纯文本帮助。

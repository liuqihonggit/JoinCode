## 调研结论

### 配置层现状（4 个并发限制，1 个死配置）

| 配置点 | 默认值 | 是否被消费 | 作用域 |
|--------|--------|-----------|--------|
| `AgentSettings.MaxConcurrentAgents` (`AgentSettings.cs:12`) | 10 | ❌ 死配置（全项目仅 1 处引用=定义处） | Agent 并发 |
| `ExecutionOptions.MaxConcurrentTasks` (`ExecutionOptions.cs:6`) | 12 | ✅ `TaskExecutor.cs:184` | Scheduling 任务并发 |
| `CacheAndToolExecutionSettings.MaxParallelToolExecution` | 5 | ✅ `QueryLoopMiddleware.cs:53` | 工具并行执行 |
| `ClusterExecutionOptions.MaxConcurrency` | 运行时传入 | ✅ `AgentExecutionEngine.cs:29` | 集群执行并发 |

### 派发路径（9 条 spawn 链路，spawn 阶段无限流）

1. **Unified Spawn 管道**（主路径）— `AgentCoordinator.SpawnSubAgentAsync` → `_spawnPipeline`，`LifecycleSpawnMiddleware` 直接 `AgentFactory.Create` 无限流
2. **批量 Spawn** — `SpawnSubAgentsAsync` → `Task.WhenAll(spawnTasks)` 全部并行，无任何限流
3. **Fork 路径** — `ForkSubAgentManager.ForkAsync`，`_lock=SempahoreSlim(1,1)` 仅保护字典，不限制并发 fork 数
4. **Scheduling 并行执行** — `TaskExecutor.ExecuteAgentsParallelAsync` 用 `Math.Min(count, CpuParallelism.GetDegree(MaxConcurrentTasks))`
5. **AgentExecutionEngine** — 真正限流点 `semaphore = new SemaphoreSlim(maxConcurrency)`，但仅限 execute 阶段
6. **Teammate Spawn** — `TeammateSpawnMiddleware` / `InProcessTeammateTask`
7. **Work Spawn** — `WorkSpawnMiddleware`
8. **Agent Background Spawn** — `AgentBackgroundSpawnMiddleware`
9. **WorkflowTask** — `ExecuteAgentTaskStepAsync`（串行单步）

### 关键缺陷

1. `MaxConcurrentAgents=10` 是死配置（定义了从未被读取）
2. spawn 阶段无限流（`SpawnSubAgentsAsync` 用 `Task.WhenAll` 全并行，fork 无限）
3. 配置分散 4 处，语义混乱，无统一入口
4. spawn 与 execute 分离（spawn 创建 worktree 占资源但不限流，仅 execute 限流）

## Claude Code 子代理策略调研（2026-09-02 联网）

### 来源

- Agent Teams: https://docs.anthropic.com/en/docs/claude-code/agent-teams

### Claude Code 策略总结

| 维度 | Claude Code 策略 | 本项目对比 |
|------|-----------------|-----------|
| **并发上限** | **无硬性上限**（"no hard limit on teammates"），靠 token 成本 + 协调开销自然约束 | 本项目同进程，需硬性上限（内存/线程池共享） |
| **推荐规模** | 3-5 teammates 起步，15 独立任务用 3 teammates | 本项目默认 8 spawn / 12 execute / 6 fork |
| **深度限制** | 子代理可 spawn 子代理（有 depth limit）；agent teams **禁止嵌套** | 本项目有 `CalculateForkDepth` |
| **隔离** | `isolation: worktree` 独立 git worktree，自动清理 | 本项目有 `WorktreeSpawnMiddleware` |
| **后台/前台** | 默认后台，后台工具集受限；fork 跳过过滤 | 本项目有 `RunBackgroundForkAsync` |
| **配置位置** | **也分散**：frontmatter + settings.json + env + CLI flag | 本项目 ADR-0048 收口到 `SubAgentConcurrencyOptions` 更统一 |
| **进程模型** | 独立进程（in-process / split-pane tmux/iTerm2） | 本项目同进程（.NET 单进程） |

### 关键启示

1. **Claude Code 也没有统一配置位置** — frontmatter（子代理定义）+ settings.json（teammateMode/env）+ CLI flag + 环境变量，四源分散。本项目 ADR-0048 的 `SubAgentConcurrencyOptions` 收口到单一类，**比 Claude Code 更统一**。

2. **"几百个子代理"靠独立进程 + token 成本约束** — Claude Code 的 agent teams 每个 teammate 是独立 Claude Code 进程，不共享内存，token 成本线性扩展自然限制。本项目是同进程 .NET，共享内存和线程池，**必须硬性上限**。

3. **保留三阶段差异化** — Claude Code 靠"无上限 + 成本感知"，本项目靠"三阶段硬性上限"（spawn/execute/fork 资源类型不同）。统一到一个配置类但保留三个字段，而非单一数值。

4. **默认值可适当提高** — 参考 Claude Code "3-5 起步可扩展"思路，本项目默认值（8/12/6）可考虑提高到（16/24/12）以支持更大规模，但仍保留硬性上限防资源耗尽。

1. **`GoalGraph.MaxConcurrency=0` 默认无限** — research 模板有并行节点（research_a ∥ research_b），无限流可能压垮资源

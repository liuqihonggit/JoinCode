# 覆盖全部功能总测试任务清单

> 关联: [启动参数完全重构任务清单](启动参数完全重构任务清单.md) (阶段6.1 仅补 21 命令,76 命令待补)
> ADR: [0069](../adr/0069-cli-args-full-refactor.md) (slash_call/mcp_call 元命令)、[0083](../adr/0083-e2e-script-mode-spec.md) (E2E 脚本模式)
> 渐进式执行: 每步编译+测试+提交

## 任务目标

构建一个 **CLI 脚本驱动的总测试**,覆盖全部 MCP 工具(382 个) + 全部斜杠命令(97 个),执行 **全参数填充**(每个工具/命令的所有参数都传有效值),并通过 `--debuglog` 步骤追踪 **深入验证命令是否真正完成任务**(而非仅参数存在/不崩溃)。

## 背景与痛点

**痛点(用户手动测试发现)**: 当前 E2E 测试只能验证参数是否存在,不能深入到命令内部环节,导致命令可能因某条件不满足就提前退出,而测试仍判通过 — 即"假绿"。需要可观测性看到命令执行到哪一步、在哪里退出。

**现有最接近的先例**:
- `tests/Integration/Integration.Tests/McpTools/McpToolSmokeTests.cs:101` — `All_Registered_Tools_Can_Be_Called_Without_Crash`,遍历所有工具 + `BuildMinimalArguments` 构造最小参数 + 调用验证不崩溃。但只填 Required 参数,不验证任务完成,无步骤追踪。
- `McpToolRegistrationValidationTests.cs` — 验证 schema 完整性(Required∈Properties、无重名、必需参数有描述),未验证参数命名统一性/类型标注完整性。

## 现状分析(2026-09-12)

| 维度 | MCP 工具(382 个) | 斜杠命令(97 个) |
|------|------|------|
| 结构化参数标注 | 911 个 `[McpToolParameter]` 特性,平均 2.4/工具,充分 | 仅 21 命令有 `[ChatCommandArg]`,**76 个(78%)只有 ArgumentHint** |
| schema 查询格式 | 统一 ToolSchema(`jcc mcp_schema --json`) | 统一 ToolSchema(`jcc slash_schema --json`),但 76 个降级为 ArgumentHint |
| 调用格式 | `key=value` / JSON / `--args-file` / `--args-stdin` | **只接受 JSON 字符串**(`SlashCommandExecutors.cs:20`) |
| 参数绑定 | 生成器统一生成参数提取代码 | 各命令自己解析 `Arguments` 字符串,无统一绑定 |

**结论**: MCP 工具侧已统一,可直接写脚本。斜杠命令侧有两个缺口: ① 78% 无结构化 schema ② 调用格式单一(只 JSON)。

### 主任务: CLI 脚本驱动全参数填充总测试

> 用户决策: 日后再进行脚本。这是覆盖全部功能的总测试,勿忘。

#### 脚本设计

```
脚本流程(每个工具/命令):
1. jcc mcp_list --json --brief          → 全部工具名(382)
2. jcc mcp_schema <tool> --json         → 参数 schema(Properties/Required/Enum/Default)
3. 生成全参数填充(移植 BuildMinimalArguments 的 30 种启发式 + 扩展可选参数也填)
4. jcc mcp_call <tool> k=v ... --json --debuglog
   ├─ stdout: {ok,data,meta} 或 {ok:false,error:{code,message,hint}}
   └─ stderr: [STEP] 执行步骤追踪 ← 深入内部环节,定位"条件不满足提前退出"
5. 解析 → 判断 ok/data 实质内容/error 退出原因 + stderr 步骤摘要
6. 副作用验证(对有副作用的工具: 写文件→验证文件存在, git→验证 git status)
7. 汇总 Markdown 报告(工具|参数|ok|步骤|退出原因|副作用验证)

斜杠命令同理: slash_list → slash_schema → slash_call --json --debuglog
```

#### 实现步骤

- [ ] 编译 jcc.exe(`dotnet publish` 或 `dotnet build -c Debug`,确认产物路径)
- [ ] 编写 PowerShell 脚本 `tests/scripts/Invoke-AllMcpAndSlashTests.ps1`(或 tools/ 下)
- [ ] 参数生成器: 移植 `BuildMinimalArguments`(`McpToolSmokeTests.cs:43-99`)的 30 种参数名启发式映射,扩展为也填充可选参数

- [ ] 小规模验证: 先跑 10 个工具验证流程(清单→schema→参数→调用→解析→报告)

#### --debuglog 步骤追踪

- `--debuglog` 是全局选项(`app/JoinCode/Cli/Core/CommandLineOptions.cs:77`),等效 `JCC_DEBUGLOG=1`
- 启用后 `Diag.WriteLine("[STEP] ...")` 输出执行步骤到 stderr
- 脚本捕获 stderr,提取 `[STEP]` 行作为执行轨迹,定位命令在哪一步因条件不满足退出

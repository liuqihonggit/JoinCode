# 脚本超时关键字自动捕获 + 路径乱码直接报错修复计划

> 创建时间: 2026-09-04
> 状态: implemented
> 关联 ADR: 待创建(涉及权限检查链顺序调整,属于架构级决策)

## 一、背景与问题

### 问题1: 脚本 wait 关键字导致默认超时终止

**现象**: AI 执行含 `Start-Sleep -Seconds 60`、`sleep 60`、`timeout /t 60` 等等待关键字的脚本时,默认 120s 超时可能不足(若脚本还有其他耗时操作),或 AI 传入的 timeout 参数小于脚本内等待时间,导致命令被强制终止,AI 收到超时错误但不知道根因是参数冲突。

**当前设计**:
- `AbsoluteTimeoutMiddleware.cs:26` 强制截断超时,默认 120s
- `ShellSearchTimeoutMiddleware.cs:11` 仅对搜索命令(rg/grep/find)缩短超时到 30s
- `ShellValidationMiddleware.cs:19` 验证 timeout 参数范围(1000-600000ms),验证失败返回 `ToolResult.Error` 给 AI
- **缺失**: 没有解析脚本内容中 wait/sleep/Start-Sleep/timeout 关键字并自动捕获时间的机制

**期望**:
1. 检测脚本内 wait/sleep/timeout 等关键字,自动提取等待时间
2. 据此调整超时上限,规避默认超时终止
3. 当用户传入 timeout < 脚本内等待时间时,直接报错给 AI(而非抛异常给软件)

### 问题2: 路径乱码触发信任路径拦截而非直接报错

**现象**: LLM 输出乱码路径(如 `D:\project\w2\ä¸­æ\æ¶å¤\ææ¡.txt`),该路径在工作目录外且不存在。当前 `PathPermissionChecker` 走到步骤9 `Ask("路径在允许的工作目录之外,需要用户确认")`,拦截等候用户确认。用户被迫手动拒绝,体验差且不合理——路径乱码本应直接报错"路径不存在"。

**当前设计**:
- `PathPermissionChecker.cs:141` 的 9 步决策链只判断路径是否在工作目录内、是否匹配规则,**不检查路径是否存在**
- 路径不存在检查分散在 `FileToolHandlers.cs:683`/`SearchToolHandlers.cs:182` 的实际文件操作时(后置检查)
- `PathValidator.cs:10` 检测路径逃逸模式(../、~/、/etc/),直接返回 `Invalid`

**期望**:
1. 权限检查阶段(前置)对**工作目录外的读取路径**检查存在性
2. 路径不存在 → 直接报错给 AI(新增 `Invalid` 枚举值),不拦截等候用户确认
3. 工作目录内路径不检查(支持创建新文件)

## 三、实现计划

### 阶段A: 脚本超时关键字自动捕获

#### A1. 新增超时关键字解析器

**文件**: `core/execution/Hands/src/ToolHandlers/Handlers/SystemTools/Shell/ShellTimeoutKeywordExtractor.cs`(新增)

**职责**: 解析脚本命令,提取内含的最大等待时间(秒)

**解析范围**(全 shell + cmd + 内嵌脚本):

| Shell | 关键字 | 示例 | 提取规则 |
|-------|--------|------|----------|
| PowerShell | `Start-Sleep` | `Start-Sleep -Seconds 60`、`Start-Sleep -Milliseconds 60000`、`Start-Sleep 60` | `-Seconds`/`-Milliseconds` 参数,或位置参数 |
| Bash | `sleep` | `sleep 60`、`sleep 0.5m`、`sleep 2h` | 位置参数 + 后缀 s/m/h/d |
| Bash | `wait` | `wait`、`sleep 5 && wait` | `wait` 本身不耗时(等子进程),不计入;但 `sleep N && wait` 计入 sleep |
| cmd.exe | `timeout` | `timeout /t 60`、`timeout /t 60 /nobreak` | `/t` 参数 |
| cmd.exe | `ping` 延迟技巧 | `ping -n 60 127.0.0.1 > nul` | `-n` 参数(每秒1次ping) |
| Python 内嵌 | `time.sleep` | `python -c "import time; time.sleep(60)"`、`python -c "time.sleep(60)"` | 正则匹配 `time\.sleep\((\d+\.?\d*)\)` |
| C# 内嵌 | `Thread.Sleep` | `dotnet script -e "Thread.Sleep(60000)"` | 正则匹配 `Thread\.Sleep\((\d+)\)`,单位毫秒 |

**API 设计**:
```csharp
public static class ShellTimeoutKeywordExtractor
{
    /// <summary>
    /// 从命令文本中提取最大等待时间(秒)。返回 null 表示无等待关键字。
    /// </summary>
    public static int? ExtractMaxWaitSeconds(string command);
}
```

**实现要点**:
- 用 `FrozenDictionary<ShellType, IKeywordPattern[]>` 组织多 shell 模式
- 每个模式用正则匹配,提取时间值,统一转换为秒
- 取所有匹配中的最大值(脚本可能有多个 sleep)
- 纯静态方法,无副作用,AOT 友正

#### A2. 新增超时关键字中间件

**文件**: `core/execution/Hands/src/ToolHandlers/Handlers/SystemTools/Shell/ShellTimeoutKeywordMiddleware.cs`(新增)

**职责**: 调用解析器,根据提取的等待时间调整超时或报错

**管线位置**: 插入到 `ShellSearchTimeoutMiddleware` 之后、`AbsoluteTimeoutMiddleware` 之前

**逻辑**:
```
1. maxWait = ShellTimeoutKeywordExtractor.ExtractMaxWaitSeconds(context.Command)
2. 若 maxWait is null → 直接 next(无等待关键字)
3. requiredTimeout = maxWait + config.TimeoutKeywordBufferSeconds (默认 30s 缓冲)
4. effectiveTimeout = context.OverrideTimeout ?? context.Timeout ?? config.DefaultTimeoutSeconds * 1000
5. 若 requiredTimeout > effectiveTimeout:
   a. 若 context.Timeout is not null (用户显式传入):
      → 冲突! 返回 ToolResult.Error 给 AI:
        "命令内含 {maxWait}秒等待,但传入超时 {context.Timeout/1000}秒不足。
         请增大 timeout 参数到至少 {requiredTimeout}秒,或移除脚本内等待关键字。"
   b. 若 context.Timeout is null (未显式传入,用默认):
      → 自动延长: context.OverrideTimeout = requiredTimeout * 1000
      → 继续执行 next
6. 若 requiredTimeout <= effectiveTimeout → 直接 next(现有超时足够)
```

**冲突报错关键**: 返回 `ToolResultBuilder.Error().WithText(...).WithDiagnostic(...).Build()`,**不抛异常**,错误抛给 AI

# 命令拦截架构改造

> 状态:进行中
> 创建:2026-08-23
> 目标:建立面向未来大量拦截需求的统一命令拦截架构,替换分散的改写器+独立拦截中间件模式

## 1. 背景与问题诊断

### 现状

Shell 命令管道(`composition/Pipelines/src/Registration/PipelineComposition.cs:244-259`):

```
Validation → Rewrite → PathGate → Classification → SedIntercept → Background → BuildIntercept → Execution → Output
```

- `ShellCommandRewriteMiddleware` 调用 `CommandRewriterRegistry`,后者收集 `ICommandRewriter`(`GhPrBodyRewriter`/`GhTimeoutRewriter`/`VpnRouteRewriter`),只能**改写**命令
- `ShellSedInterceptMiddleware`、`ShellBuildInterceptMiddleware` 是独立中间件,各自短路拦截,有状态(sed 两阶段确认、build 队列等待)

### 问题

1. **`ICommandRewriter` 只能改写不能拒绝** — 接口 `string Rewrite(...)`(`ICommandRewriter.cs:22`)只能返回改写后的命令,无法表达"拒绝并提示""转交专用工具"。导致"拒绝 git commit 引导 /commit"无法用改写器实现,被迫新建独立中间件
2. **拦截器分散,管道顺序靠人肉维护** — Sed/Build 拦截器各占一个槽位,顺序在 `PipelineComposition.cs` 硬编码。每加一个拦截需求就要写中间件类 + 插管道 + 祈祷别插错位置
3. **改写与拦截职责割裂** — "给 gh pr 加 --body"(改写)和"拦截 dotnet build"(拦截)本质都是"命令执行前干预",却用两套机制,优先级无法跨机制统筹
4. **不可扩展** — 未来大量拦截需求(敏感命令确认、外网拦截、rm 拦截、git push 拦截等)会让管道膨胀到不可维护

## 2. 架构总览

**分层决策 + 链式调度**,按"是否有状态/异步"分两层:

```
┌─────────────────────────────────────────────────────┐
│           CommandInterceptionDispatcher             │
│                                                     │
│  阶段1: Guard 链(无状态瞬时决策,按 Priority 升序)   │
│    Allow → 继续 | Rewrite → 改写+继续 | Deny → 短路  │
│    Redirect → 短路(引导) | Handoff → 进阶段2        │
│                                                     │
│  阶段2: Interceptor 链(有状态异步,按 Priority 升序) │
│    Handled → 短路 | Continue → 继续                 │
│                                                     │
│  阶段3: 放行 → next(context)                        │
└─────────────────────────────────────────────────────┘
```

- **Guard 层**:无状态、纯决策、可同步。适合拒绝/改写/转交/放行
- **Interceptor 层**:有状态、可异步、可短路。适合两阶段确认/队列等待/交互对话
- **Dispatcher**:统一调度两层,按 Priority 排序,收集 DI 自动注册的实现
- **管道**:单一中间件 `ShellCommandInterceptionMiddleware` 占一个槽位,调用 Dispatcher

### 为什么不强制全状态机

简单拒绝不需要状态机。状态机**局部化**在需要的 interceptor 内部(如 sed 的 Idle→Previewing→Applying 封装在 `SedInterceptor` 里,框架只看到 Handled/Continue)。简单场景零负担,复杂场景自管状态。

## 3. 核心抽象(接口设计)

### 3.1 决策模型 `CommandDecision`

```csharp
public abstract record CommandDecision
{
    /// 放行,继续下一个 guard
    public sealed record Allow : CommandDecision;

    /// 改写命令,更新命令后继续链(允许链式改写)
    public sealed record Rewrite(string NewCommand, string? Reason = null) : CommandDecision;

    /// 硬拒绝,短路返回诊断
    public sealed record Deny(ToolDiagnostic Diagnostic) : CommandDecision;

    /// 转交专用工具,短路返回引导提示(软引导,由 LLM 自行调用)
    public sealed record Redirect(string TargetTool, string Hint, ToolDiagnostic? Diagnostic = null) : CommandDecision;

    /// 降级到 Interceptor 层处理(需交互/状态的决策)
    public sealed record Handoff : CommandDecision;
}
```

### 3.2 守卫 `ICommandGuard`(无状态)

```csharp
public interface ICommandGuard
{
    /// 优先级(数值越小越先评估)
    int Priority { get; }

    /// 守卫名称(日志/调试)
    string Name { get; }

    /// 是否处理该命令(快速过滤,避免无关节点 Evaluate)
    bool CanHandle(string command, IReadOnlyDictionary<string, object> context);

    /// 评估决策(纯函数,无副作用)
    CommandDecision Evaluate(string command, IReadOnlyDictionary<string, object> context);
}
```

### 3.3 拦截器 `ICommandInterceptor`(有状态)

```csharp
public interface ICommandInterceptor
{
    int Priority { get; }
    string Name { get; }

    bool CanHandle(string command, IReadOnlyDictionary<string, object> context);

    /// 处理命令,可异步、可有状态、可短路
    Task<InterceptResult> HandleAsync(
        string command,
        IReadOnlyDictionary<string, object> context,
        CancellationToken ct);
}

public abstract record InterceptResult
{
    /// 已处理,短路返回此结果
    public sealed record Handled(ToolResult Result) : InterceptResult;

    /// 未处理,继续下一个 interceptor
    public sealed record Continue : InterceptResult;
}
```

### 3.4 调度器 `CommandInterceptionDispatcher`

```csharp
public sealed class CommandInterceptionDispatcher
{
    /// 注入所有 guard 和 interceptor(DI 自动收集)
    public CommandInterceptionDispatcher(
        IEnumerable<ICommandGuard> guards,
        IEnumerable<ICommandInterceptor> interceptors,
        ILogger? logger = null);

    /// 调度:Guard 链 → Interceptor 链 → 放行
    /// 返回 null 表示放行(命令可能已被改写,通过 out 参数返回最终命令)
    public async Task<ToolResult?> DispatchAsync(
        ShellPipelineContext context,
        CancellationToken ct);
}
```

调度逻辑:
1. **Guard 链**(按 Priority 升序):依次 `Evaluate`
   - `Allow` → 继续
   - `Rewrite` → `context.Command = newCmd`,继续(链式改写)
   - `Deny` → 返回 `ToolResult.Error(diag)`
   - `Redirect` → 返回 `ToolResult` 含引导提示
   - `Handoff` → break,进阶段2
2. **Interceptor 链**(按 Priority 升序):依次 `HandleAsync`
   - `Handled` → 返回 `result`
   - `Continue` → 继续
3. **放行** → 返回 `null`(中间件调 next)

## 4. 管道集成

### 4.1 新中间件

`ShellCommandInterceptionMiddleware` 替代 `ShellCommandRewriteMiddleware`,占同一槽位:

```csharp
[Register]
public sealed partial class ShellCommandInterceptionMiddleware : ServiceEntity, IShellMiddleware
{
    public async Task InvokeAsync(ShellPipelineContext context, MiddlewareDelegate<ShellPipelineContext> next, CancellationToken ct)
    {
        var rewriteContext = new Dictionary<string, object> { ["ShellKind"] = context.Provider.Kind };
        var result = await _dispatcher.DispatchAsync(context, ct);
        if (result is not null)
        {
            context.Result = result;  // 短路
            return;
        }
        await next(context, ct);  // 放行
    }
}
```

### 4.2 管道顺序(改造后)

```
Validation → Interception(统一) → PathGate → Background → Execution → Output
```

- `Classification` 评估保留(它做命令分类,非拦截)
- Sed/Build 拦截器从独立中间件迁移为 interceptor,由 Dispatcher 调度,不再占独立槽位

## 5. 迁移映射

| 现有 | 迁移为 | 层 | 说明 |
|------|--------|----|------|
| `ICommandRewriter` | `ICommandGuard` | Guard | 接口替换,返回 CommandDecision 而非 string |
| `GhPrBodyRewriter` | `GhPrBodyGuard` | Guard | `Rewrite` 决策 |
| `GhTimeoutRewriter` | `GhTimeoutGuard` | Guard | `Allow`(仅日志) |
| `VpnRouteRewriter` | `VpnRouteGuard` | Guard | `Rewrite` 或 `Allow` |
| `CommandRewriterRegistry` | 并入 `CommandInterceptionDispatcher` | 调度 | 删除独立 registry |
| `ShellCommandRewriteMiddleware` | `ShellCommandInterceptionMiddleware` | 管道 | 升级 |
| `ShellSedInterceptMiddleware` | `SedInterceptor : ICommandInterceptor` | Interceptor | 状态机内部保留 |
| `ShellBuildInterceptMiddleware` | `BuildInterceptor : ICommandInterceptor` | Interceptor | 队列逻辑内部保留 |

### 优先级规划

| Guard/Interceptor | Priority | 理由 |
|-------------------|----------|------|
| `GitCommitGuard`(新) | 10 | 安全拒绝优先 |
| `VpnRouteGuard` | 30 | 网络路由 |
| `GhTimeoutGuard` | 50 | 超时控制 |
| `GhPrBodyGuard` | 100 | 参数补全(最后,改写不影响前面决策) |
| `SedInterceptor` | 100 | sed 拦截 |
| `BuildInterceptor` | 200 | build 拦截(sed 优先) |
